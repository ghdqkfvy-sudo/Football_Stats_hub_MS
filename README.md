# MS Stats Hub

레알 마드리드 · 첼시 · 대한민국 — 한 앱에서 팀을 전환하며 보는 축구 통계 허브.
**모든 날짜와 시각은 한국시간(KST) 기준**이며, 데이터는 하드코딩이 아니라 실시간으로 받아온다.

```
ksh/
├─ web/          React + TypeScript + Vite (PWA)
├─ worker/       Cloudflare Worker — ESPN 프록시 + 캐시
├─ scripts/      GitHub Actions 스냅샷 수집기
└─ .github/      10분 주기 cron 워크플로
```

---

## 1. 데이터 소스

주력은 **ESPN 공개 엔드포인트**다. API 키가 없고 공표된 호출 제한도 없는, 사실상 유일한 선택지였다.

| 용도 | 엔드포인트 |
|---|---|
| 팀 일정(지난/예정) | `site.web.api.espn.com/apis/site/v2/sports/soccer/all/teams/{id}/schedule[?fixture=true]` |
| 리그 순위 | `site.api.espn.com/apis/v2/sports/soccer/{league}/standings` |
| 대회 참가팀 | `site.api.espn.com/apis/site/v2/sports/soccer/{league}/teams` |
| 경기 요약·라인업 | `site.api.espn.com/apis/site/v2/sports/soccer/{league}/summary?event={id}` |
| 득점자·어시스트 | `sports.core.api.espn.com/v2/sports/soccer/leagues/{league}/events/{id}/competitions/{id}/plays` |
| 선수 시즌 스탯 | `sports.core.api.espn.com/v2/sports/soccer/leagues/{league}/seasons/{yyyy}/types/1/athletes/{id}/statistics` |

검증된 팀 ID: **레알 마드리드 86 · 첼시 363 · 대한민국 451**

### 구축 중 확인한 함정 4가지

1. **순위는 `/apis/v2/` 경로다.** `/apis/site/v2/.../standings` 는 축구에서 빈 객체 `{}` 를 돌려준다.
2. **어시스트는 `summary` 에 없다.** 골과 별개의 `"Assists Shot"` 플레이로 `/plays` 에만 들어오며,
   `clock.value` 로 골 이벤트와 조인해야 한다. (`src/lib/normalize.ts` 의 `goalsFromPlays`)
3. **`details[]` 가 비어서 오는 경기가 있다.** 같은 경기라도 응답마다 채워지는 필드가 다르다.
   그래서 정규화 레이어 전체가 "있으면 쓰고 없으면 넘어간다" 방어적 파싱이고,
   득점 상세는 `/plays` 를 1순위로 쓴다.
4. **순위 응답이 낡아서 올 때가 있다.** 라리가는 각 팀이 5경기를 치른 시점에 `gamesPlayed: 3`,
   챔피언스리그 2026-27은 1차전이 끝났는데 32팀 전원 0경기 0점으로 왔다. 그래서 `buildTable()` 이
   ESPN 표를 참가팀 시드로만 쓰고, 경기 기록이 ESPN 집계를 **모든 팀에 대해** 따라잡았을 때만
   결과로 표를 다시 만든다(부분 데이터로 표를 망치지 않기 위한 조건이다).

5. **호스트에 따라 다른 시즌이 온다.** 챔피언스리그 순위를 `site.api` 로 부르면 2026-27,
   `site.web.api` 로 부르면 2025-26 최종 표가 왔다. 폴백이 조용히 다른 시즌을 물어오지 않도록
   시즌 확인이 필요하다.

### 보조 소스 (선택)

- **TheSportsDB** — 엠블럼·선수 사진 (무료 키 `123`, 30회/분)
- **API-Football** — 교차검증용 (무료 100회/일, 코리안리거 다중 리그 커버)
- football-data.org 는 무료 티어에 **득점자·라인업이 없어** 채택하지 않았다.

## 2. 아키텍처 — 왜 프록시와 스냅샷을 같이 쓰는가

```
GitHub Actions (10분 cron) ──ESPN──▶ web/public/data/*.json ──커밋──┐
                                                                   ▼
사용자 ──────────────────────────────▶ Cloudflare Pages (CDN, 정적 읽기 무제한)
   └── 경기 진행 중에만 ──▶ Cloudflare Worker (10만 req/일) ──▶ ESPN
```

- 평상시 읽기는 **전부 CDN** 에서 나간다 → 사용자가 늘어도 ESPN 호출은 0건.
- ESPN 실호출은 Actions에서 하루 수백 건 → 차단 위험 없음.
- 실시간성이 필요한 순간에만 Worker가 30초 TTL로 통과시킨다.
- **전 구간 무료**: public 레포는 Actions 무료, Pages 정적 요청 무제한, Worker 10만/일.

### 순위표를 직접 계산하는 이유 (실측)

2026-09-14 기준 ESPN 집계와 실제 진행 라운드가 이만큼 어긋나 있었다.

| 대회 | ESPN standings | 실제 |
|---|---|---|
| 라리가 | 3R | **5R** 진행 |
| 프리미어리그 | 2R | **4R** 진행 |
| 챔피언스리그 2026-27 | 32팀 전원 0경기 0점 | 1차전 종료 |

그래서 `buildTable()` 은 ESPN 표를 **참가팀 명단 시드**로만 쓰고, 대회의 모든 경기
기록으로 표를 다시 만든다. 단 우리 기록이 ESPN 집계를 *모든 팀에 대해* 따라잡았을
때만 대체하고(부분 데이터로 표를 망치지 않기 위해), 그때는 섹션 라벨이
"경기 결과로 산출 · 5R 반영"으로 바뀐다.

### ⚠️ scoreboard 의 날짜 범위는 조용히 잘린다

`scoreboard?dates=A-B` 로 여러 날을 한 번에 받으면 응답이 **경고 없이 잘려서**
일부 경기가 빠진다. 이걸 모르고 쓰다가 라리가 50경기 중 43경기만 수집돼
팀마다 3~5경기로 집계가 어긋나고 순위표가 틀어졌다.

신뢰할 수 있는 수집 경로는 두 가지다.
1. **팀별 `/teams/{id}/schedule`** — 한 팀의 전 경기를 빠짐없이 준다. Worker 의
   `/api/v1/league/:slug` 가 이 방식을 쓴다.
2. **하루 단위 `scoreboard?dates=YYYYMMDD`** — 응답이 작아 잘리지 않는다.

두 경로로 교차 검증한 결과가 스냅샷(`src/data/lamatches.ts`)이다.
검증 스크립트로 경기 수·팀별 출전 수·스코어와 득점 기록 일치를 모두 확인했다:
라리가 50경기 149골, 프리미어리그 37경기 102골, 불일치 0건.

### 코리안리거 데이터 경로

ESPN 에는 "한국인 해외파" 목록이 없다. 그래서 **대표팀 스쿼드에서 역산**한다.

1. `core /leagues/fifa.friendly/seasons/2026/teams/451/athletes` → 선수 ID 26명
   (ESPN 은 `$ref` 로만 준다)
2. `core /athletes/{id}` → 이름·포지션·나이 + **소속 클럽 ID**
3. `core /teams/{id}` → 클럽 이름
4. `core /leagues/{league}/seasons/2026/types/1/athletes/{id}/statistics` → 시즌 기록

한 선수당 3번의 왕복이 필요하므로 Worker 가 서버에서 모아 캐시한다.
국내 리그(울산 HD) 소속은 "리거"가 아니라 제외했다.

⚠️ `site.../teams/451/roster` 는 응답이 커서 **수비수까지만 잘려서** 온다.
공격수·미드필더를 얻으려면 위의 core 경로를 써야 한다.

**대표팀 스쿼드 밖 선수**(양민혁·이현주·김민수 등)는 검색 API 로 찾는다.
`site.web.api.espn.com/apis/search/v2?query=…` 의 `uid` 가 `s:600~a:371578` 형태라
뒤의 숫자가 곧 athlete id 다. 검색 결과의 `id` 필드는 UUID 라 core API 에 쓸 수 없다.

**대회별 기록은 리그와 유럽대항전을 각각 조회해야 한다.** 한 선수의 전 대회 기록을
합쳐 주는 엔드포인트가 없어서 `leagues/{league}/…/athletes/{id}/statistics` 를
리그 슬러그마다 따로 부른다. 화면에는 리그와 챔스/유로파/컨퍼런스만 노출한다.

### 베스트 11 은 어떻게 뽑는가

경기별 라인업은 core API 에만 있다.

```
sports.core.api.espn.com/v2/sports/soccer/leagues/{league}
  /events/{id}/competitions/{id}/competitors/{teamId}/roster
```

여기에 `formation.summary`("4-2-3-1")와 선수별 `formationPlace`, `starter`,
`subbedIn/Out` 이 들어 있다. 출전·선발·출전시간을 여기서 뽑고, 득점·도움은
경기 득점 이벤트에서 붙여 시즌 집계를 만든다.

⚠️ **`formationPlace` 는 줄 번호가 아니다.** ESPN 이 포메이션마다 정해 둔
슬롯 번호이고 줄 순서와 일치하지 않는다. 레알 마드리드 6경기를 교차 검증해
4-2-3-1 의 슬롯 의미를 확정했다:

| 슬롯 | 1 | 2 | 3 | 5 · 6 | 4 · 8 | 7 | 10 | 11 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| 자리 | GK | RB | LB | CB | 수비형 MF | 우측 MF | 공격형 MF | 좌측 MF | ST |

검증하지 않은 포메이션은 **추측하지 않고** 포지션 그룹(G/D/M/F)으로 배치하고,
UI 에 "포지션 그룹 배치"라고 밝힌다(`src/lib/squad.ts`).

**선수 목록 정렬**은 베스트 11 을 먼저 두되 포메이션 위쪽(공격)부터 — FW → MF → DF → GK —
나열하고, 나머지는 선발 많은 순 → 출전 많은 순 → 득점 많은 순으로 잇는다(`orderForList`).

**헤드샷**은 `a.espncdn.com/i/headshots/soccer/players/full/{athleteId}.png` 를 쓰고,
이미지가 없거나 차단되면 등번호 배지로 폴백한다.

### 어시스트는 별도 경로

`details[]`(스코어보드·요약)에는 **득점자만** 들어 있다. 어시스트는 core API 의
`/plays` 에 `"Assists Shot"` 이라는 별개 이벤트로만 존재하며, 골 이벤트와
`clock.value` 로 조인해야 한다. 종료 경기의 기록은 변하지 않으므로 Worker 에서
7일 캐시한다. 스냅샷 프리뷰에서는 미리 받아 둔 경기에만 어시스트가 있다.

### 대회 묶음 라우트

`/api/v1/league/:slug` 는 참가팀 명단 → 각 팀 일정 → 대회 경기만 추려 하나로 합쳐 준다.
이 한 번의 응답으로 순위표·홈/원정 기록·공격포인트가 모두 계산되므로 클라이언트 왕복이 없다.

⚠️ Cloudflare 무료 플랜은 **호출당 서브리퀘스트 50건** 제한이 있다. 그래서 팀별로
`schedule` 을 한 번만 부른다(예정 경기는 일정 탭의 팀 스케줄에서 이미 받는다).
36팀 대회 기준 38건으로 한도 안에 들어간다.

### Worker 캐시 계층

| 대상 | TTL | 근거 |
|---|---|---|
| 진행 중 경기 | 30초 | 스코어 갱신 |
| 일정 · 순위 | 10분 | 실질 변동 주기 |
| 선수 시즌 스탯 | 6시간 | 경기 후에만 변함 |
| **종료 경기 득점 기록** | 7일 | 다시 바뀌지 않음 |

## 3. KST 처리

단순 시각 변환만으로는 부족하다. **캘린더 날짜 칸 배정이 KST 기준이어야** 한다.
UTC 날짜로 버킷팅하면 `2026-09-15T19:30Z` (= 9월 16일 04:30 KST) 경기가 15일 칸에 박힌다.

KST는 UTC+9 고정이고 서머타임이 없어 타임존 DB 없이 오프셋만으로 정확히 계산된다 →
`src/lib/kst.ts` 의 `dayKey()` 가 캘린더 그룹핑의 유일한 기준이다.
새벽 경기(00:00–05:59 KST)에는 자동으로 `새벽` 배지가 붙는다.

## 4. 실행

```bash
# 웹앱
cd web && npm install && npm run dev          # 스냅샷 모드 (프록시 없이 동작)
VITE_API_BASE=http://localhost:8787 npm run dev   # 실시간 모드

# Worker
cd worker && npm install && npm run dev       # wrangler dev
npm run deploy                                # Cloudflare 배포

# 스냅샷 수동 실행
node scripts/snapshot.mjs web/public/data
```

배포 시 `web/.env.production` 에 `VITE_API_BASE=https://<worker>.workers.dev` 를 넣는다.
`VITE_API_BASE` 가 비어 있으면 앱은 자동으로 스냅샷 모드로 떨어지며, 헤더 배지가
`실시간` / `스냅샷` 중 무엇으로 동작 중인지 항상 표시한다.

## 5. 디자인

다크 단일 테마로 확정하고, 팀 전환 시 `--brand / --accent / --on-accent / --glow`
네 개의 CSS 변수만 교체한다. 뉴트럴은 순수 회색이 아니라 파랑 쪽으로 살짝 기운 값
(야간 조명 색온도)을 쓴다. 대회별 색은 팀 컬러와 독립적으로 고정이다.

- 타이포: `Archivo`(팀명·본문) / `Barlow Condensed`(스코어·카운트다운·분 단위 기록) / `Noto Sans KR`(한글 폴백)
- 바탕은 검정이 아니라 **짙은 네이비**(`--ink-1000: #061127`). 레퍼런스의 야간 경기장 톤에 맞췄다
- 배경: 팀 아트워크 + 팀 그라데이션 오버레이. 고정 레이어라 페이지 전체에 같은 밀도로 깔리고,
  사진은 `brightness(.42)` 로 눌러 하이라이트가 글자를 먹지 않게 한다
- 캘린더는 패널 없이 배경 위에 얹고 해어라인 격자만 남긴다. 이달의 경기는 네이비 패널로 떠오른다
- 경기장은 실제 규격(105 × 68 m)을 그대로 SVG 좌표로 써서 페널티 에어리어·골 에어리어·
  페널티 아크·코너 호 비율이 맞다(`PitchMarkings.tsx`)
- 선수 호버 카드의 득점·도움·공격포인트는 팀 컬러 글로우로 강조한다
- 대회 색은 리그 브랜드를 따른다 — 라리가 레드, 프리미어리그 퍼플, 챔피언스리그 블루
- 캘린더는 칸마다 대회 컬러 막대만 두고(종료=채움 / 예정=테두리), 점수·득점자는 호버 카드로 넘긴다
- 데스크톱 호버로 보여주는 정보(캘린더 경기 결과)는 모바일에서 **탭 → 바텀시트**로 자동 전환된다.
- 엠블럼 로딩 실패 시 이니셜 배지로 폴백한다(국가대표팀은 ESPN 로고 경로가 불안정해 처음부터 이쪽을 쓴다).

임대·바이백·셀온 **조항은 계약 정보라 어떤 무료 API에도 존재하지 않는다.**

### 다음 경기 히어로 — 순위·승무패 (2026-09-16)

최근 5경기 폼 칩을 걷어내고 **리그 순위 + 승/무/패 + 승점**으로 바꿨다.
`ScheduleTab` 이 순위표를 직접 받아 주입한다.

- 1순위: 그 경기의 대회 순위표 (챔스 리그페이즈 포함)
- 2순위: 우리 팀 리그 순위표
- 둘 다에 없는 팀(컵대회 하위리그 상대 등)은 그 영역을 비운다

`buildTable` 을 그대로 재사용하므로 ESPN 표가 밀려 있을 때의 재계산 규칙도 순위탭과 동일하다.

### 레퍼런스 정렬 리빌드 (2026-09-16)

사용자 레퍼런스 이미지와 맞지 않던 부분을 토큰 단위부터 다시 잡았다.

**배경** — `brightness(.42)` 로 사진을 죽여 놓고 그 위에 82% 베일을 덮어
"이미지 25% / 그라데이션 75%" 비율이 사실상 0% 가 되어 있었다.
밝기는 살리고(`brightness(.62)`) 비율은 베일 알파(`.78`)로만 만든다.

**패널** — 레퍼런스에는 칠한 패널이 없다. 히어로·캘린더·이달의 경기·경기장·
선수 리스트를 모두 `rgba(6,16,38,.16~.30)` + 헤어라인 테두리로 바꿔
배경 아트워크가 패널 안쪽까지 비친다.

**히어로** — 3열 그리드(홈/센터/원정)를 버리고 레퍼런스 구조로 재작성했다.
`다음 경기` 골드 필 → 엠블럼 두 장 + VS → `19위 · 0W 2D 3L` 요약 →
날짜 → 킥오프 시각 → 카운트다운 스트립. 팀 컬러 글로우는 `.hero::before`
라디얼 그라데이션으로 카드 아래쪽에서 피어오른다.

**캘린더** — 격자선과 칸 배경을 전부 없앴다. 날짜 숫자는 칸 왼쪽 위,
대회 막대는 칸 아래. 월 제목은 가운데, 화살표는 양 끝(`grid-row: 1` 을
명시하지 않으면 제목이 열 2를 점유해 화살표가 다음 줄로 밀린다).
다음 경기 날짜는 `data-next` 로 골드 원이 채워진다.

**이달의 경기** — 대진 칸을 `118px / 56px / 118px` 3열 그리드로 고정하고
홈은 오른쪽 정렬, 원정은 왼쪽 정렬로 스코어에 붙였다. 행이 몇 개든
엠블럼·약어·스코어가 같은 세로선에 선다. 스코어는 팀 약어와 같은 스케일
(15px)이며 크기가 아니라 팀 컬러로만 도드라진다.

### 베스트 11 선정 규칙 (2026-09-16)

사용자 지정 가중치를 그대로 코드 순서로 옮겼다.

1. 그 자리(포메이션 슬롯)에서의 선발 출전 수
2. 총 출전 경기 수
3. 리그 총 출전 시간
4. 공격 포인트

중앙 미드필더 줄은 좌/우를 나누지 않는다. `lineKind()` 가 `MID` 로 판정한
줄은 그 줄의 모든 `formationPlace` 를 한 묶음으로 합산한다
(4-2-3-1 의 4·8 은 사실상 같은 자리다).

**팀 조직력** = 베스트 11 각 자리 선수의 `선발 / 최대 선발(라인업 확보 경기 수)`
평균 × 100. 같은 11명이 계속 함께 선발될수록 100 에 가까워진다.

### 선수 스탯 레이아웃 (2026-09-16)

`.squad` 에 `height: 700px` 를 못 박아 경기장과 선수 리스트의 세로 길이를
같게 만들었다. 리스트는 베스트 11(골키퍼까지) 다음부터 스크롤된다.
호버 카드는 `position: fixed` 로 그린다 — 리스트에 `overflow-y: auto` 를
걸면 `absolute` 카드가 잘리기 때문이다.

골·도움은 숫자와 함께 게이지로도 보여 준다. 기준은 절대값이 아니라
**스쿼드 최고 기록 대비 비중**이라, 한 줄만 봐도 팀 안에서 누가 해결사인지
읽힌다. 골은 팀 컬러, 도움은 시안.

### 어시스트가 0 으로 나오던 원인 (2026-09-16)

집계가 **이름 문자열 매칭**에 의존하고 있었다.

```ts
const a = m.goals.filter(x => x.assist === info.name).length;   // ← 이게 문제
```

두 겹으로 틀렸다.

1. ESPN 의 득점 이벤트(`details[]`)에는 애초에 어시스트가 거의 없다.
   core `/plays` 의 "Assists Shot" 을 따로 이어 붙여야 하는데, 그 경로가
   막히면 도움은 통째로 0 이 된다.
2. 이어 붙이더라도 `B. Díaz` / `Brahim Díaz` 처럼 표기가 달라 매칭이 깨진다.

**해결** — site 요약(`summary?event=`)의 `rosters[].roster[]` 를 라인업 소스로
쓴다. 여기에는 `formationPlace`·`starter` 와 함께 선수별 `totalGoals`,
`goalAssists` 가 **athleteId 와 같이** 들어 있다. 이름 매칭이 사라지고,
PK·자책골 처리도 ESPN 집계 그대로 따라간다.

- Worker: `matchroster/:league/:event/:team` 추가 (요약에서 rosters 만 잘라 반환)
- `LineupEntry` 에 `골, 도움` 두 칸을 더하고 `Lineup.hasStats` 로 구분
- `buildSquad` 는 `hasStats` 면 그 값을, 아니면 예전 이름 매칭으로 폴백

검증(레알 마드리드 6경기): 비니시우스 3도움, 벨링엄 2도움, 음바페 1도움,
발베르데 1도움, 트렌트 1도움, 브라힘 1도움 — ESPN gamelog 와 일치한다.
(이전에는 브라힘 1도움만 잡혔다)

### 뉴스 탭 (2026-09-16)

두 소스를 합친다.

- ESPN 팀 뉴스: `site/v2/sports/soccer/{league}/news?team={id}`
- 한국어: 구글 뉴스 RSS — `news.google.com/rss/search?q=…&hl=ko&gl=KR&ceid=KR:ko`

한국어 기사는 무료·무키 소스가 사실상 구글 뉴스 RSS 뿐이라 Worker 의
`newsko?q=` 가 XML 을 파싱해 JSON 으로 바꿔 준다. CORS 와 파싱을 모두
엣지에서 끝내기 위해서다. 구글은 제목 끝에 ` - 매체명` 을 붙이는데
`<source>` 와 중복이라 떼어 낸다.

⚠️ 구글 뉴스 RSS 는 개발 샌드박스에서 robots.txt 로 막혀 있어 **이 저장소에서
직접 응답을 확인하지 못했다.** 파싱은 방어적으로 짰고(항목이 하나도 안 나오면
ESPN 기사만 보여 준다), 배포 후 첫 확인이 필요하다.

한쪽 피드가 실패해도 나머지는 그대로 보여 준다 — 뉴스는 전부-아니면-전무가
아니어도 쓸모가 있다.

### Future Resources 탭 (2026-09-16)

이적 조항(바이백 금액, 셀온 비율, 임대 의무구매)은 **어떤 무료 API 에도 없다.**
그래서 역할을 쪼갰다.

- `web/src/data/future.ts` — 조항 정보만 손으로 관리 (athleteId + 조항 문구)
- ESPN — 현 소속팀·출전·득점·도움·최근 경기를 athleteId 로 실시간 조회
  (Worker `gamelog/:league/:athleteId`)

선수가 팀을 옮겨도 ID 만 맞으면 화면이 따라간다. ID 를 모르면
`find?q=이름` 으로 찾는다(응답 `uid` `s:600~a:337970` 의 뒤 숫자).

큐레이션 원칙: **확인되지 않은 금액·비율은 적지 않는다.** 지어낸 숫자가
하나라도 들어가면 이 탭 전체를 믿을 수 없게 된다. 현재 시드는 조항의
'종류'까지만 적고, 금액은 비워 두었다.

### 순위가 갱신되지 않던 이유 — 빠져 있던 2단계 (2026-09-16)

데이터 경로는 원래 3단계로 설계했다.

| 단계 | 출처 | 신선도 |
|---|---|---|
| 1 | Worker 프록시 → ESPN 직접 호출 | 실시간 |
| 2 | GitHub Actions 가 떠 두는 `/data/*.json` | 10분 ~ 1시간 |
| 3 | 번들에 박힌 TS 스냅샷 | 고정 |

**2단계가 코드에 연결돼 있지 않았다.** 워크플로는 돌고 `web/public/data/` 에
파일도 쌓이는데 앱이 그 파일을 한 번도 읽지 않았다. 그래서 `VITE_API_BASE`
(Worker 주소)가 없으면 곧장 3단계 — 2026-09-14 에 박아 둔 고정값 — 으로
떨어졌고, 순위가 영원히 그 날짜에 멈춰 있었다. Artifact 프리뷰는 애초에
네트워크가 막혀 있으니 항상 3단계다.

고친 것:

- `loadSchedule` / `loadLeague` 가 **프록시 → 정적 피드 → 번들** 순으로 내려간다.
- `Source` 에 `'feed'` 를 추가하고, 헤더 배지와 순위 탭에 **출처와 기준 시각**을
  같이 적는다(`고정 스냅샷 9. 14. 오전 07:30 기준`). 순위가 이상해 보일 때
  제일 먼저 필요한 정보는 "언제 뜬 값인가" 다.

### 스냅샷 수집 범위 확대 (2026-09-16)

기존 스크립트는 우리 세 팀 일정과 순위표만 떴다. 그런데 **ESPN 의 순위표는
실제 경기보다 몇 라운드씩 늦는다** — 라운드 6 이 끝난 날에도 "2경기 소화" 로
내려오는 것을 확인했다. 그래서 앱은 경기 결과로 표를 다시 계산하는데
(`league.ts`), 그러려면 그 리그 **모든 팀**의 경기가 필요하다.

`scripts/snapshot.mjs` 가 이제 리그별로 전 팀 일정을 모아 `league-{slug}.json`
으로 저장한다. `scoreboard?dates=A-B` 는 응답이 조용히 잘리므로
(라리가 50경기 중 43경기만 들어와 순위가 틀어진 적이 있다) 팀별 schedule 을
합치는 방식만 쓴다.

무게가 달라서 워크플로를 둘로 쪼갰다.

- `snapshot.yml` — 우리 세 팀 일정, 6요청, **10분** 주기
- `snapshot-leagues.yml` — 리그 전 팀(리그당 20팀 × 2요청) + 순위, **1시간** 주기

한 워크플로에서 다 돌리면 10분마다 120요청이 나가 ESPN 에 과하다.

### 하드코딩 전면 제거 (2026-09-16)

앱 번들에 **경기 데이터가 하나도 없다.** 화면의 모든 숫자는 Worker 프록시의
실시간 응답이거나 `scripts/snapshot.mjs` 가 ESPN 에서 떠 온 JSON 이다.

삭제한 파일: `data/snapshot.ts`, `data/lamatches.ts`, `data/leagues.ts`,
`data/lineups.ts`, `data/koreans.ts`, `data/news.ts` (합계 약 1,100줄).
번들 305 kB (이전 344 kB).

남긴 것은 **설정**뿐이다 — 데이터가 아니다.

| 파일 | 왜 코드에 있나 |
|---|---|
| `config/targets.ts` | 어떤 팀·대회를 보여 줄지, 색·표기 |
| `config/koreans.ts` | "누구를 코리안리거로 볼 것인가" 는 편집 판단. **ID 와 정렬 규칙만**, 기록은 0줄 |
| `data/future.ts` | 이적 조항은 어떤 API 에도 없다 |

**폴백 사슬에서 번들을 뺐다.** 예전에는 프록시가 없으면 박아 둔 값으로
내려가서, 화면은 멀쩡한데 순위와 일정만 조용히 틀려졌다. 이제 프록시도
피드도 없으면 `source: 'none'` 이고 화면이 그렇게 말한다. 틀린 값을 조용히
보여 주는 쪽이 빈 화면보다 훨씬 나쁘다.

### 시즌 자동 판정 (2026-09-16)

`SEASONS = ['2026-27', '2027-28']` 를 없앴다. 유럽 시즌은 8월에 시작하므로
오늘(KST)의 월이 8 이상이면 그 해가, 아니면 전 해가 시즌 시작 연도다
(`kst.ts` 의 `seasonStartYear`). 수집 스크립트도 같은 규칙으로 ESPN 의
`seasons/{year}` 를 고른다. 해가 바뀌어도 손댈 곳이 없다.

### 수집 범위 (scripts/snapshot.mjs)

이 스크립트가 만드는 파일이 곧 앱이 아는 세상의 전부다.

    meta.json              언제 떴는지
    schedule-{slug}.json   팀 일정 (일정 탭 · 다음 경기)
    league-{slug}.json     리그 전 팀 경기 + 순위 (순위 탭)
    squad-{slug}.json      경기별 라인업 + 선수별 골·도움 (선수 스탯 탭)
    koreans.json           코리안리거 소속 · 대회별 기록 · 최근 경기
    news-{slug}.json       ESPN 영문 + 한국어 구글 뉴스
    future.json            조항 선수들의 현재 기록

무게가 달라 두 갈래로 돈다.

- `--only=fast` — 팀 일정·뉴스. 가볍다 → **10분** (`snapshot.yml`)
- `--only=slow` — 리그 전 팀·스쿼드·코리안리거 → **1시간** (`snapshot-leagues.yml`)

### 프리뷰 빌드의 인라인 피드

`vite.config.single.ts` 는 `public/data/*.json` 을 빌드 시점에 인라인한다.
Artifact 처럼 네트워크가 막힌 곳에서도 열어 보기 위해서다. 손으로 적은 값이
아니라 `npm run snapshot` 이 떠 온 파일 그대로이고, 화면에는 `자동 갱신 · N일 전`
처럼 기준 시각이 항상 같이 나온다. `public/data` 가 비어 있으면 아무것도
인라인되지 않고 "데이터 없음" 이 그대로 보인다.

로컬에서 채우는 법:

    cd web
    npm install
    npm run snapshot     # ESPN → public/data/*.json
    npm run dev          # 또는 npx vite build --config vite.config.single.ts

### 공격 포인트 3분할 (2026-09-16)

탭으로 전환하던 득점 / 도움 / 공격포인트를 **세 표로 한 번에** 보여 준다.
"누가 넣고 누가 만들어 줬는지" 를 비교하려면 예전에는 매번 클릭해야 했다.

게이지는 팀 컬러 그라데이션이다. 세 지표가 전부 accent 하나로 칠해지면
막대만 봐서는 어떤 표인지 구분이 안 되므로 **도움만 방향을 뒤집는다.**

| 표 | 그라데이션 |
|---|---|
| 득점 | accent → secondary |
| 도움 | secondary → accent |
| 공격 포인트 | accent → secondary |

기준값(100%)은 각 표의 1위 — 그 선수단의 최고 기록이다. 절대값이 아니라
팀 안에서의 비중으로 읽힌다. 숫자는 세 표 모두 팀 컬러(accent)에 글로우를
얹고, 지표 구분은 게이지 방향이 맡는다.

`TargetTheme` 에 `secondary` 를 추가했다 — 레알은 보라(#8B7BFF),
첼시는 엠블럼 금색(#F5C451), 대한민국은 태극기 청색(#4C8DFF).
`--secondary` 로 내려가므로 팀을 바꾸면 게이지도 같이 바뀐다.

### GitHub 저장소 · GitHub Pages 배포 (2026-09-16)

프로젝트를 git 저장소로 초기화하고, `main` 에 푸시할 때마다 GitHub Pages 로
자동 배포되도록 `.github/workflows/deploy-pages.yml` 을 추가했다.

**중요한 점**: 이 배포는 `snapshot.yml`/`snapshot-leagues.yml` 봇 커밋으로도
매번 다시 트리거된다. 즉 10분/1시간마다 최신 ESPN 데이터가 `web/public/data/*.json`
으로 커밋되고, 그 커밋이 Pages 재빌드를 일으켜 **정적 피드 데이터가 배포된
사이트에 그대로 반영**된다 — 여기에도 하드코딩된 값은 없다.

- `vite.config.ts` 에 `base` 를 추가해 GitHub Pages 프로젝트 페이지
  (`https://<user>.github.io/<repo>/`) 서브패스에서도 정적 자산 경로가 깨지지
  않게 했다 (`BASE_PATH` 환경변수, 워크플로우가 저장소 이름으로 자동 설정).
- `manifest.webmanifest` 와 `sw.js` 도 절대경로(`/…`) 하드코딩을 제거하고
  상대경로 / `registration.scope` 기반으로 바꿔 서브패스에서도 정상 동작한다.
- 실시간 프록시 티어(Cloudflare Worker)를 쓰려면 저장소 Settings → Secrets
  and variables → Actions → **Variables** 에 `VITE_API_BASE` 를 등록한다.
  비워 두면 정적 피드 티어만으로 동작한다(하드코딩 아님, 자동 갱신 그대로).

배포 저장소에 처음 올릴 때 필요한 절차 (저장소 생성 → 첫 푸시 → Pages 활성화)는
`gh`/GitHub 계정 인증이 필요해 에이전트 세션에서 대신 실행할 수 없다. 사용자가
직접 실행할 명령은 대화에서 안내한다.

### GitHub Pages/Actions 무료 티어 신뢰성 검토 (2026-09-16)

"GitHub으로 배포하면 실시간 데이터 유지가 되는지" / "서버가 꺼지진 않는지"
질문에 대한 조사 결과.

**결론: 이 프로젝트 규모에서는 GitHub 쪽에 실질적인 단점이 없다.**

- GitHub Pages는 정적 호스팅(CDN)이라 애초에 "꺼진다"는 개념이 없다 —
  Render/Railway/Fly.io 무료 플랜처럼 일정 시간 요청이 없으면 슬립되고
  콜드스타트로 깨워야 하는 서버가 아니다.
- Actions의 `schedule` 트리거는 60일간 저장소에 커밋이 전혀 없으면
  자동 비활성화되는데, 우리 스냅샷 워크플로우 자체가 10분/1시간마다
  커밋을 만들어내므로 이 조건에 걸릴 일이 사실상 없다(닭이 알을 낳는 구조).
- 퍼블릭 저장소는 GitHub Actions 실행 시간이 사실상 무제한/무료다(프라이빗
  저장소만 월 2,000분 한도).
- `actions/deploy-pages` 로 배포하는 경우(우리 설정) 예전 Jekyll 브랜치
  빌드에만 적용되던 "시간당 10회 빌드" 제한이 적용되지 않는다 — 10분마다
  재배포돼도 문제없다. 월 100GB 대역폭 소프트 리밋만 남아있는데 개인
  프로젝트 트래픽으로는 넉넉하다.
- 유일한 진짜 캐치: `schedule` 은 "최선 노력" 방식이라 정각(0, 10, 20분…)처럼
  요청이 몰리는 시각엔 실행이 5~30분 밀릴 수 있다(GitHub 공식 문서에 명시).
  → 그래서 `snapshot.yml` 의 분(minute)을 `3,13,23,33,43,53` 으로 옮겨
  정각 혼잡을 피했다. "꺼지는" 게 아니라 "가끔 늦게 도는" 정도의 오차다.

**대안을 검토한다면:** Netlify는 이미 다른 용도로 쓰고 있다고 해서 뺐고,
나머지 무료 옵션들은 이 구조엔 오히려 안 맞거나 더 나쁘다.

| 옵션 | 이 프로젝트에 안 맞는 이유 |
|---|---|
| Vercel Hobby | Cron Jobs가 하루 1회로 제한됨(2026년 기준) — 10분 주기 불가 |
| Render 무료 | 웹 서비스가 15분 무응답 시 슬립 → 콜드스타트 필요(우리가 피하려는 문제) |
| Railway | 2023년에 무료 티어 자체가 없어짐(소액 체험 크레딧뿐) |
| Fly.io | 2025~26년에 무료 할당량 대부분 폐지, 사실상 유료 |
| Cloudflare Pages | 빌드 500회/월 무료 — 10분마다 재배포하면 한 달에 수천 회라 이 캡에 걸림 |

**단, Cloudflare Workers(이미 `worker/` 에 준비해 둔 실시간 프록시)는
그 자체로 훌륭한 조합이다**: 요청 10만 회/일 무료, Cron Trigger 지원(계정당
5개, 분 단위 가능), 서버 개념이 없어 잠들지도 않는다. 지금 구조(정적 피드는
GitHub Pages, 실시간 프록시만 Cloudflare Worker)가 두 서비스의 장점을 각자
잘 쓰는 조합이라 그대로 가는 걸 추천한다. 나중에 더 손보고 싶다면 스냅샷
자체를 GitHub Actions 대신 Cloudflare Worker Cron Trigger + KV로 옮겨서
"커밋→재배포" 없이 엣지에서 바로 갱신하는 방법도 있다 — 지금 당장 필요한
변경은 아니고, 트래픽이 커지면 고려할 선택지로 남겨둔다.

### 배포 후 1차 개선 묶음 — 캘린더·이달의 경기·선수 스탯 (2026-09-16)

첫 배포 후 발견된 13건을 한 번에 처리했다. 확신도가 다르므로 구분해 적는다.

**확실히 고친 것 (동작으로 검증 가능):**

- 캘린더에서 선택한 날짜의 경기 막대(bar)가 펄스닷과 같은 리듬으로
  커졌다 작아졌다 한다(`.bar[data-sel='true']` + `@keyframes barPulse`,

  정정해 줘서 다시 만들었다.
- 캘린더 호버는 실제 마우스 기기(`hover: hover` 미디어쿼리)에서는 그대로
  마우스오버로 뜨고, 터치 기기에서는 첫 탭에 미리보기만 뜨고 한 번 더
  눌러야 상세가 열린다(터치엔 호버 개념이 없어 탭으로 대신한 것 — 완전히

- 캘린더 호버 카드에서 예정 경기 칸의 중복된 날짜 숫자를 지웠다(장소만 남김).
- "이달의 경기" 제목 옆 경기 숫자 배지를 지웠다.

- 선수 스탯 집계에서 클럽 친선경기(`club.friendly`)를 제외했다(국가대표
  친선전은 정식 A매치라 그대로 집계).
- 공격 포인트 순위를 8등까지 보여주되, 동점자는 같은 등수를 받고(1,2,2,4식)
  "8등까지"는 줄 수가 아니라 등수 기준으로 판정한다 — 8등이 여럿이면 전부 보인다.
- 첼시 포메이션: ESPN의 `formationPlace` 번호가 뜻하는 자리가 팀마다(어쩌면
  데이터 소스마다) 다를 수 있다는 게 실측으로 확인됐다. 레알 마드리드는
  6경기로 직접 검증된 자리 배치를 계속 쓰고, 검증되지 않은 팀(첼시 포함,
  앞으로 추가될 팀도 자동으로 포함)은 틀린 자리를 확신 있게 보여주는 대신
  포지션 그룹 기준(수비/중원/공격)으로 정직하게 배치한다 — 화면에도
  "포지션 그룹 배치"라고 표시된다.
- 선수 헤드샷: ESPN 축구 API/CDN이 선수 개인 사진 자체를 제공하지 않는다는
  걸 실제 선수 ID(손흥민·비니시우스 주니어)로 확인했다(전부 404, 응답
  어디에도 headshot 필드 없음). "잘못된 URL을 찾는" 문제가 아니라 데이터가
  없는 것이어서, 실패할 요청을 계속 쏘는 대신 바로 등번호 배지를 보여주도록
  바꿨다. ESPN이 나중에 제공하면 `Headshot.tsx`의 `ATTEMPT_IMAGE` 하나만
  켜면 된다.

**다음 경기 히어로 — 날짜 선택과 연동:**

캘린더에서 다른 날짜를 누르면 상단 히어로가 그 날짜의 경기로 바뀐다(예정이면
카운트다운, 진행 중이면 "진행 중" + 스코어, 종료됐으면 "경기 결과" + 최종
스코어). 선택한 날짜에 경기가 없으면 원래의 "다음 경기"로 돌아간다.

**득점자 기록 누락 · 대회 순위 미갱신 — 근본 원인과 조치:**

두 문제(이달의 경기 득점자 누락, 대회별 공격포인트 순위 미갱신) 모두 같은
원인이었다: ESPN 팀 일정(`schedule`) 응답에는 애초에 `details[]`(득점자
필드)가 없다 — 요약(`summary`) 엔드포인트에만 있는 필드다. 정적 피드만
보는 배포(GitHub Pages, Worker 프록시 없음)에서는 경기를 하나씩 클릭해
불러오는 지연 로딩(`loadGoals`)도 Worker가 없으면 실패해서, 득점 기록이
통째로 비어 있었다.

조치: `scripts/snapshot.mjs`가 스냅샷을 뜰 때 종료된 경기마다 core API
`/plays`를 한 번 더 불러 득점자+어시스트를 미리 구워서
`competitions[0].__goals`에 박아 둔다(클라이언트의 기존
`goalsFromPlays()`와 같은 로직). 한 번 뜬 경기는 이전 스냅샷에서 이어받아
다시 조회하지 않는다(종료된 경기의 득점 기록은 안 바뀌므로). 클라이언트
`normalize.ts`는 `__goals`가 있으면 그걸 쓰고, 없으면(Worker 응답 등)
기존 방식(`details[]`)을 그대로 쓴다.

첫 실행에서는 시즌 전체 종료 경기 분량을 한 번에 받아오느라 평소보다
오래 걸릴 수 있다(리그당 최대 수백 경기, 요청 사이 0.15초 대기) — 이후
실행부터는 새로 끝난 경기만 조회한다.

**출전시간 — 부분 완료:**

선수 스탯의 출전시간이 "경기수 × 90분"으로 뭉뚱그려지는 문제. ESPN 경기별
교체 시각 필드(`subbedInAtMinute`/`subbedOutAtMinute`)는 실제 응답에
이름 그대로 있는지 검증되지 않아 대부분 비어 온다. 대신 이미 코리안리거
집계에서 검증된 경로 — 선수 시즌 통계(`/athletes/{id}/statistics`)의
실제 누적 출전 분(`minutes`/`timePlayed`) — 를 `scripts/snapshot.mjs`가
스쿼드를 뜰 때 선수별로 한 번 더 조회해서 `athletes[id].minutesSeason`에
채워 넣고, `web/src/lib/squad.ts`가 있으면 그 실제값으로 총 출전시간을
덮어쓴다. **다만 경기별 상세 내역(레이더/최근 경기 카드의 분당 기록)은
여전히 어림값이다** — 실제로 바뀐 건 "총합"뿐이고, 이 부분을 실제 기록으로
바꾸려면 경기별 교체 시각의 정확한 ESPN 필드명을 먼저 확인해야 한다.

**적용 방법:** 위 변경은 코드에 반영됐고 로컬 빌드(`npm run build`)로
타입체크·번들링까지 확인했다. 실제 배포에 반영하려면 평소처럼 GitHub에
푸시하면 된다 — `scripts/snapshot.mjs`가 바뀌었으므로 다음 스냅샷 실행
(최대 1시간 이내, 또는 Actions 탭에서 수동 실행)부터 득점자·출전시간이
채워진다.

### 2차 개선 — 데이터가 한 번도 갱신되지 않던 진짜 이유 (2026-09-16)

1차 개선 이후에도 득점자·출전시간·순위가 그대로였다. 원인을 파 보니
**코드 문제가 아니라 워크플로우가 매번 죽고 있었다.**

#### ① 스냅샷 커밋이 항상 실패하고 있었다 (치명적)

```
no changes added to commit (use "git add" and/or "git commit -a")
Process completed with exit code 1.
```

원인은 커밋 단계의 순서였다.

```bash
git add web/public/data          # ← 스테이징
git pull --rebase --autostash    # ← autostash 가 스테이징까지 stash 했다가
                                 #    되살릴 때 "스테이징 안 된 상태"로 되돌린다
git commit -m ...                # ← 그래서 커밋할 게 없다며 exit 1
```

`--autostash` 는 stash 를 되살릴 때 인덱스(스테이징) 상태를 보존하지 않는다.
즉 **ESPN 데이터는 매번 정상적으로 받아 왔는데, 커밋 직전에 전부 스테이징이
풀려서 한 번도 저장소에 올라가지 못했다.** 배포된 사이트가 계속 옛 데이터를
보고 있던 근본 원인이다. `pull` 을 먼저 하고 그다음에 `add` 하도록 순서를
바꿔 두 워크플로우 모두 고쳤다.

#### ② `/plays` 로는 애초에 골을 못 가져온다 (1차 개선의 설계 오류)

1차 개선에서 득점 상세를 core API `/plays?limit=400` 으로 받도록 했는데,
실제 응답을 확인해 보니 **한 경기가 1,404개 플레이**(패스·터치·걷어내기까지
전부)로 내려온다. limit 400 이면 경기 시작 후 3분치만 들어와서 골이 단
하나도 안 잡힌다. (`worker/src/index.ts` 의 `goals` 라우트도 같은 한계를
갖고 있다 — 프록시를 쓰더라도 골이 비는 이유다.)

대신 **스코어보드**를 쓰도록 바꿨다. 실측 결과(2026-09-12 eng.1) 스코어보드는
`competitions[0].details[]` 에 그 날짜·그 대회 **모든 경기**의 득점 상세를
한 번의 요청으로 준다:

```json
{"type":{"text":"Goal"},"clock":{"displayValue":"7'"},"team":{"id":"363"},
 "scoringPlay":true,"penaltyKick":false,"ownGoal":false,"athletesInvolved":[…]}
```

그래서 경기 단위가 아니라 **날짜 단위**로 한 번씩만 받아 나눠 붙인다.
요청 수가 경기 수에서 날짜 수로 줄어드는 덤도 있다. 한 번 채운 경기는
이전 스냅샷에서 이어받아 다시 조회하지 않는다.

한계 하나: 스코어보드 `athletesInvolved` 는 보통 득점자만 준다. 그래서
대회 전체 순위표의 **도움** 칸은 여전히 비게 된다(우리 세 팀의 선수 스탯
도움은 경기 로스터의 `goalAssists` 에서 오므로 영향 없다).

#### ③ 첼시 베스트 11 — formationPlace 를 믿으면 안 된다

ESPN 첼시 2026-09-12 헐시티전(4-2-3-1) 라인업을 그대로 받아 대조했다.

| formationPlace | 1 | 3 | 6 | 5 | 2 | 4 | 8 | 11 | 10 | 7 | 9 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| ESPN 포지션 | G | LB | CD-L | CD-R | RB | LM | RM | AM-L | AM | AM-R | F |

기존 코드가 쓰던 표(레알 마드리드 경기로 눈대중해 맞춘 것)는 수비 줄을
`3, 5, 6, 2` 로 봤는데 **실제로는 `3, 6, 5, 2`** 다 — 센터백 두 자리가
좌우 반대였다. 즉 번호의 의미가 팀/데이터 소스마다 달라질 수 있다.

그래서 배치 근거를 번호에서 **ESPN 이 주는 포지션 약어**로 전부 옮겼다.
약어에는 역할(`G`·`CD`·`LB`·`DM`·`M`·`AM`·`F`…)과 좌우(`-L`/`-R` 접미,
`L`/`R` 접두)가 그대로 들어 있어서 추측할 여지가 없다. 배치 규칙은
"약어에서 깊이(수비→공격)와 좌우를 읽어 포메이션 줄에 채운다" 한 줄이다.

결과적으로 **팀별 "검증된 포메이션" 목록이 필요 없어졌다.** 새 팀을
추가해도 ESPN 이 준 자리 그대로 그려진다. 위 실측 라인업을 그대로 넣어
다섯 줄이 정확히 `GK / LB·CD-L·CD-R·RB / LM·RM / AM-L·AM·AM-R / F` 로
나오는 것까지 확인했다.

#### ④ 출전시간 — 데이터 경로는 맞았다

`/athletes/{id}/statistics` 를 실제로 조회해 확인했다(콜윌, eng.1 2026):
`appearances: 3`, `starts: 3`, **`minutes: 252`**. 3×90=270 이 아니라 252 —
교체 아웃이 반영된 진짜 기록이다. 즉 1차 개선의 코드 경로는 옳았고,
①번 커밋 실패 때문에 그 값이 한 번도 배포되지 않았을 뿐이다.

#### ⑤ 그 밖에

- 캘린더 선택 날짜의 경기 막대 펄스가 위아래뿐 아니라 **좌우로도** 커진다
  (`scale(1.22, 2.2)`). 날짜 칸 밖으로 넘쳐도 잘리지 않는다.
- 순위표 어코디언(홈/원정 결과)에서 아직 치르지 않은 **예정 경기 줄을
  뺐다** — 그 자리는 결과를 보는 곳이고, 일정은 일정 탭에 있다.

### 헤드샷 — 앞선 결론이 틀렸다 (2026-09-16)

1차 개선에서 "ESPN 은 축구 선수 사진을 제공하지 않는다"고 결론 내리고
이미지 시도를 아예 꺼 버렸다(`ATTEMPT_IMAGE = false`). **그 결론이 틀렸고,
끈 것 자체가 사진이 하나도 안 나오게 만든 원인이었다.**

다시 확인한 사실:

| 확인한 곳 | 사진 필드 |
|---|---|
| 선수 프로필 `/athletes/{id}` | 없음 |
| 경기별 로스터 (summary rosters) | 없음 |
| 검색 API | 없음 |
| **팀 로스터 `/teams/{id}/roster`** | **`headshot.href` 있음** |

즉 사진의 존재 여부를 알려 주는 응답은 **팀 로스터 하나뿐**이고, 처음엔
그 한 곳만 안 봤다. CDN 주소 패턴은 원래 쓰던 것과 같다 — 다만 **일부
선수만** 사진이 있다:

```
a.espncdn.com/i/headshots/soccer/players/full/353951.png  → 이미지 있음
a.espncdn.com/i/headshots/soccer/players/full/296410.png  → 404
a.espncdn.com/i/headshots/soccer/players/full/149945.png  → 404
```

처음 확인할 때 하필 사진이 없는 선수(손흥민·비니시우스)만 찍어 보고
"아예 없다"고 일반화한 것이 오진의 원인이었다.

조치:

- `scripts/snapshot.mjs` 가 팀 로스터를 팀당 한 번 받아 선수별 실제 주소를
  `athletes[id].photo` 로 박아 둔다(코리안리거는 소속팀 로스터에서, 팀
  단위로 캐시). 스냅샷 로그에 `사진 N명` 이 찍히므로 몇 명이나 확보됐는지
  Actions 로그에서 바로 보인다.
- `Headshot` 은 그 실제 주소를 우선 쓰고, 없으면 관용 주소를 시도한 뒤
  실패하면 등번호·이니셜 배지로 떨어진다(`onError`).

#### 보유율이 정말 그렇게 낮은지 다시 확인했다

"첼시에 사진이 3장뿐일 리 없다"는 지적을 받고 다시 검증했다. 지적대로
**로스터 응답을 읽던 도구가 중간에서 잘리고 있었다**(24명까지만 보였다).
그래서 개수를 CDN 주소로 직접 찔러 교차 확인했다:

| 선수 ID (첼시 선발) | 결과 |
|---|---|
| 158626 · 270190 · 296410 · 308947 | 404 |
| 353951 (Hato) | 이미지 있음 |

레알 마드리드 로스터도 같은 방식으로 보니 16명 중 1명이었다. 즉 **잘림은
사실이었지만(내가 말한 "3장"은 근거가 약했다), 보유율이 낮다는 결론 자체는
직접 찔러 본 결과로도 그대로**다. 실제 개수는 팀당 3~6명 선일 수 있다 —
스냅샷은 Actions 에서 잘리지 않은 전체 응답을 읽으므로 있는 대로 다 가져온다.

#### 그래서 위키백과로 보충한다

ESPN 에 사진이 없는 선수는 위키백과 대표 이미지를 찾아 채운다. 엉뚱한
사람 얼굴이 뜨는 건 사진이 없는 것보다 나쁘므로 관문을 세 개 뒀다.

1. 문서 설명에 `footballer`/`football`/`soccer` 가 있어야 한다 (동명이인 배제)
2. 문서 제목이 선수 이름과 맞아야 한다 (발음기호·대소문자·하이픈 무시하고 비교)
3. SVG 는 버린다 (문서에 사진이 없으면 위키가 축구공 아이콘을 대표 이미지로 준다)

셋 중 하나라도 어긋나면 사진 없이 배지로 둔다. 관문 로직은 실제 사례
(Vinícius Júnior → Vinicius Junior, Son Heung-Min → Son Heung-min, 동명이인
정치인, SVG 아이콘 등)로 테스트했다. 한 번 찾은 주소는 다음 스냅샷에서
이어받아 다시 조회하지 않는다.

⚠️ 위키백과 호출 자체는 이 작업 환경에서 도메인이 막혀 있어 **실제 응답으로
검증하지 못했다.** Actions 에서 처음 돌 때 로그의 `사진 ESPN n + 위키 m`
숫자로 확인할 수 있다. 실패해도 배지로 떨어질 뿐 다른 데이터에는 영향이 없다.

### 헤드샷·퓨처·최근경기 — 세 화면이 비어 있던 이유 (2026-09-22)

배포된 사이트를 열어 세 가지를 고쳤다. 셋 중 둘은 **원인이 같았다.**

#### ① 레알 마드리드만 헤드샷이 나왔다 — TheSportsDB 요청 한도

스냅샷 파일에서 사진 출처를 세어 보니 원인이 분명했다.

| 팀 | TheSportsDB | 위키백과 | 없음 |
|---|---|---|---|
| real-madrid | **25** | 0 | 4 |
| chelsea | 6 | 12 | 6 |
| man-united | 0 | 20 | 2 |
| tottenham | 0 | 23 | 1 |
| newcastle | 0 | 19 | 7 |
| korea | 0 | 38 | 9 |

`TEAMS` 처리 순서가 `real-madrid → chelsea → man-united → tottenham →
newcastle → korea` 다. 즉 **먼저 처리한 팀이 다 써 버리고 그 뒤로는 전부
실패**했다 — 무료 키(`3`)의 요청 한도다. 같은 이름들을 개별로 조회하면
전부 컷아웃이 잘 나온다(뉴캐슬·맨유 선수 12명으로 확인). 데이터가 없는 게
아니라 한 회차에 160번을 몰아친 것이 문제였다.

그리고 폴백인 위키백과 대표 이미지는 **헤드샷이 아니다.** 250px 경기
사진이라 44px 원형 칩에 넣으면 얼굴이 아니라 잔디와 유니폼이 보인다.
그래서 "사진은 있는데 누군지 알 수 없는" 상태가 됐다.

고친 것 (`scripts/lib/photos.mjs`):

- **요청을 한 줄로 세운다** — TheSportsDB 만 최소 1.1초 간격으로 부른다.
  연속 8회 실패하면 회로를 열어 그 회차는 포기한다(막힌 API 를 200번 더
  때려 봐야 워크플로만 길어진다).
- **사진에 출처 등급을 붙인다** — `cutout > thumb > espn > wiki`.
  지난 회차 값을 후보에 같이 넣고 **등급이 높을 때만 갈아탄다.** 그래서
  ⑴ 한도에 걸린 회차에도 사진이 사라지지 않고 ⑵ 예전에 위키 사진이 박힌
  선수는 컷아웃을 받는 회차에 올라간다. 한 번에 다 못 받아도 회차를
  거듭하며 채워진다. (예전 코드는 "직접 받은 게 있으면 그걸, 없으면
  이어받기" 라서 한 번 박힌 위키 사진이 영원히 남았다.)
- **HEAD 확인을 관대하게** — 예전에는 `res.ok` 가 아니면 주소를 버렸다.
  CDN 은 HEAD 를 405/403 으로 막기도 하고 러너에서 네트워크가 튀기도
  하는데, 그때 완벽한 컷아웃 주소를 버리고 위키로 내려갔다. 이제 404/410
  일 때만 버린다.
- 화면에도 출처를 넘겨(`data-kind`) 컷아웃과 경기 사진의 크롭 위치를 다르게
  잡는다. 다만 이건 보조 수단이다 — 근본 해결은 컷아웃 커버리지다.

#### ② Future Resources 와 코리안리거 최근 3경기 — 죽은 엔드포인트 하나

`/data/future.json` 이 **404** 였고(한 번도 만들어진 적이 없다),
`koreans.json` 의 `recent` 는 **21명 전원 0건**이었다. 원인은 하나였다.

```
GET site.web.api.espn.com/apis/common/v3/sports/soccer/{lg}/athletes/{id}/gamelog
→ HTTP 500  {"code":2400}
```

어떤 리그·선수로 불러도 그렇고(`usa.1` 손흥민으로 확인), `?season=2026` 을
붙여도 같고, 옆의 `overview` 도 같이 죽었다. 수집기는 이 응답에서 경기
목록을 못 얻어 `if (!rows.length) return` 으로 전원 탈락했고 — **워크플로는
매번 초록색이었다.** 화면만 전부 `–` 였다.

살아 있는 대체 경로는 core 의 eventlog 다(모든 리그에서 200).

```
/v2/sports/soccer/leagues/{lg}/seasons/{y}/athletes/{id}/eventlog
  → events.items[] = { event.$ref, lineupEntry.$ref, statistics.$ref, teamId, played }
```

`statistics.$ref` 한 번이면 그 경기의 `appearances / minutes / starts /
subIns / totalGoals / goalAssists / yellowCards` 가 다 나온다.

⚠️ **`played: true` 를 출전으로 믿으면 안 된다.** 명단에 든 것까지 true 다
(실측: 김민재 401884801 은 `played:true` 인데 `appearances:0 · minutes:0`).
실제 출전은 경기별 statistics 로만 가른다 — 예전에 "안 뛴 경기가 교체로
찍히던" 문제를 이제 추론이 아니라 데이터로 가른다.

⚠️ eventlog 의 items 는 **날짜 순서가 아니다**(9/13 경기가 8/28 경기보다
앞에 온다). 팀 일정에서 받은 날짜로 다시 정렬한다.

덤으로 Future 의 출전수가 정확해졌다. 예전 `apps = rows.length` 는 명단에만
든 경기까지 세서 과대 집계였다(코리안리거에서 이미 고친 문제인데 이 경로에는
반영되지 않았다). 이제 시즌 통계의 `appearances` 를 쓴다.

워커의 `gamelog` 라우트도 같은 이유로 죽어 있었다 → `playerlog` 로 교체했다.

#### ③ 조용한 실패를 막는다

②가 몇 주 동안 안 보였던 건 **실패해도 워크플로가 초록색이었기 때문**이다.
이제 수집기가 장부를 들고, "만들어야 하는데 못 만들었고 대신 쓸 예전 파일도
없다" 면 워크플로를 빨갛게 만든다(`process.exitCode = 1`).

  `table-{slug}.json` 을 따로 떠서 그걸 읽는다.
- **`save()` 를 원자적으로.** 임시 파일에 쓰고 rename 한다. 워크플로가
  중간에 취소되면 잘린 JSON 이 남고 바로 다음 스텝의 `git add` 가 그걸
  커밋할 수 있었다.
- **스냅샷 워크플로의 자기 취소 제거.** `cancel-in-progress: true` + 10분
  cron 조합에서, 한 회차가 10분을 넘게 돌면(리그 잡은 실측 15분) 다음
  회차가 지금 회차를 죽이고 그 자리를 또 다음 회차가 죽였다 — 커밋 기록상
  10분 주기인데 실제 갱신은 시간당 3번뿐이었다. 겹치면 기다리게 하고
  (`cancel-in-progress: false`), cron 을 실제 소요에 맞춰 20분으로 두고,
  매달린 회차는 `timeout-minutes` 가 끊는다.
- **ErrorBoundary 추가.** 한 탭의 파싱 오류가 화면 전체를 흰 페이지로
  만들지 않는다. 방어적 파싱을 이만큼 해 두고 최후 방어선이 없었다.
- **렌더 중 컴포넌트 생성 제거.** `NextMatchHero` 의 `Team` 과
  `StandingsTable` 의 `Col` 은 부모 안에서 만들어져 렌더마다 새 컴포넌트
  타입이 됐다 — React 가 매번 통째로 다시 마운트한다(히어로는 카운트다운으로
  매초 리렌더된다). 모듈 바깥으로 끌어냈다.
- **시즌 선택기를 정직하게.** 두 개의 시즌 단추가 헤더 글자만 바꾸고
  일정·순위는 그대로였다. 시즌별 조회가 없으므로 현재 시즌을 표기만 한다.
- **데드코드 제거** — `normalize.ts` 의 `deriveStandings`/`standingsLookStale`
  (`league.ts` 의 `buildTable` 로 대체된 두 번째 구현), `App.tsx` 의
  `Placeholder`("2단계에서 구현" 문구가 남은 35줄, 6탭 모두 구현되어 조건이
  항상 false), 빈 `Test.md`·`_web/`.
- 남은 정리 하나: `standings-*.json` 3개(276KB)는 앱이 읽지 않는다 —
  `league-*.json` 과 `table-*.json` 이 standings 를 이미 품고 있다. 지금
  지우지 않은 이유는 10분마다 도는 봇이 아직 옛 코드로 그 파일을 다시
  만들기 때문이다(지우면 리베이스가 매번 충돌한다). 새 코드가 배포된 뒤
  별도 커밋에서 제거한다.
- CI 에서 playwright 브라우저(100MB+) 다운로드를 건너뛴다 —
  `web/shotH.mjs` 용 로컬 개발 의존성이다.


### 카드 통일 · 리버풀 · 히어로 순위 (2026-09-22, 2차)

#### ① 선수 카드를 한 양식으로 (`components/StatCard.tsx`)

Future Resources 는 숫자 네 칸짜리 전용 카드였고 코리안리거는 게이지가 있는
카드였다. 같은 "선수 한 명의 시즌 기록" 인데 모양이 달라 눈이 매번 다시
적응해야 했고, 고칠 일이 생기면 두 곳을 고쳐야 했다. 한 컴포넌트로 합쳤다 —
CSS 는 이미 있던 `.krc*` / `.krr*` 를 그대로 쓰고, 전용 스타일
(`.fgrid` / `.fcard*` 75줄)은 지웠다.

#### ② 게이지를 **선발 비율**로

예전 게이지는 그 대회 공격포인트를 카드 안 최댓값으로 나눈 값이었다. 그래서
골·도움이 없는 선수는 전부 0 이고, 하나라도 있으면 꽉 찬 막대가 됐다 —
사실상 "공격포인트 있음/없음" 두 값이라 아무 정보도 주지 않았다.
이제 **선발 ÷ 출전** 이다. "얼마나 주전인가" 가 이 카드에서 훨씬 많이
궁금한 값이고, 0~100% 사이에 실제로 분포한다.
(Future 카드도 같은 게이지를 쓰도록 `future.json` 에 `starts` 를 실었다.)

#### ③ 유럽대항전 0경기 줄이 사라지던 문제

스냅샷은 "이 클럽은 챔스 출전 팀인데 이 선수는 아직 출전이 없다" 를 구분해
`apps: 0` 줄을 넣어 둔다(`teamsIn(lg).has(clubId)`). 그런데 화면이
`apps > 0` 하나로 걸러서 그 줄을 통째로 지웠다 — **"챔스에 안 나가는 팀" 과
구분이 사라졌다.** 이제 유럽대항전 줄은 0경기라도 남기고, 나중에 출전하면
그 줄이 그대로 채워진다. 규칙은 `lib/comps.ts` 에 두고 테스트로 고정했다.

#### ④ 리버풀 추가

배경 사진은 아직 없다. 사진을 못 구했다고 팀 추가가 막히는 편이 더 나쁘므로
`Target.bg` 를 선택 항목으로 바꾸고, 없으면 팀 컬러 그라디언트로 떨어지게
했다. `web/src/assets/bg-liv.jpg` 를 넣고 `targets.ts` 의 `bg` 를 채우면
다른 팀과 같아진다.

#### ⑤ 히어로의 "3위 · 3승1무0패" 가 사라진 진짜 이유

일정 탭의 순위표 로딩에 경합이 있었다. `tables` 를 이펙트 의존성에 넣고,
그 안에서 `setTables` 로 로딩 표시를 넣고, 정리 함수에서 `alive = false` 로
응답을 버리는 구조였다.

```
1) 이펙트 실행 → setTables({esp.1: null}) → 요청 시작
2) tables 가 바뀌어 이펙트 재실행 → 정리 함수가 alive = false
3) 요청이 돌아옴 → if (!alive) return → 결과를 버린다
4) 재실행된 이펙트는 'esp.1' in tables 라서 다시 요청하지 않는다
```

표는 **영원히 채워지지 않았다.** 3.2MB 파일을 받던 시절에도 같았고, 응답이
느릴수록 확실히 버려졌다. 요청 이력을 상태가 아니라 `useRef` 에 두어 이펙트가
자기 자신을 다시 트리거하지 않게 하고, 응답을 버리지 않도록 했다 — 결과는
대회 슬러그로 키가 박혀 있어 늦게 와도 제자리에 들어간다.

#### ⑥ 상대전적 — 최근 세 시즌 · 5경기

클럽은 이번 시즌 + 지난 한 시즌(두 시즌)만 봤다. 리그에서 두 번 만난 기록
뿐이라 표본이 너무 얇았다. 지난 두 시즌까지 받아 **세 시즌**으로 넓히고,
목록은 최신 **5경기**까지 보여 준다.

#### ⑦ 첼시 헤드샷 세 건 — 원인이 각각 달랐다

| 선수 | 증상 | 원인 |
|---|---|---|
| 리스 제임스 | 전혀 다른 선수 얼굴 | TheSportsDB 의 유일한 "Reece James" 가 **셰필드 웬즈데이의 1993년생 동명이인**. 소속팀이 안 맞는데도 `players[0]` 로 떨어졌다 |
| 주앙 페드루 | 사진 없음(위키 경기 사진) | 이름 검색이 포르투갈 3부의 다른 Joao Pedro 만 돌려준다. 첼시 **로스터**에는 컷아웃까지 있는 `João Pedro` 가 들어 있었다 — 발음기호 때문에 검색으로는 못 찾았다 |
| 하토 | 이미지가 비어 보임 | ESPN 헤드샷(600×436)의 **위쪽 12% 가 완전 투명**이라 크롭에 빈 공간이 걸렸다. TheSportsDB 컷아웃이 있는데 한도에 걸려 못 받았다 |

고친 것:

- **팀 로스터 조회를 1순위로** (`searchteams` + `lookup_all_players`, 팀당
  2요청·캐시). 팀이 확정된 목록 안에서 찾으므로 동명이인 위험이 없고, 표기
  차이에 관대해도 안전하다. 주앙 페드루가 이 경로로 잡힌다.
- **이름 검색은 소속팀이 맞아야 채택한다.** 안 맞으면 사진을 포기한다 —
  이 프로젝트의 원칙 그대로(엉뚱한 얼굴이 사진 없음보다 나쁘다). 리스 제임스는
  이제 등번호 배지로 떨어진다.
- 성(姓)만으로 맞추는 마지막 단계는 **찾는 이름이 두 토큰 이상일 때만** 쓴다.
  "Pedro" 한 단어로 João Pedro 를 집으면 Pedro Neto 를 뜻했을 때 사고가 난다.

#### 정정 — gamelog 는 "죽었다" 가 아니라 "간헐적으로 죽는다"

1차 수정에서 `common/v3/.../gamelog` 이 죽었다고 적었다. 그 뒤 옛 코드가 도는
회차(12:26)에 그 엔드포인트가 **정상 응답해서** `future.json` 을 만든 것을
확인했다. 항상 죽은 게 아니라 간헐적으로 500 을 뱉는다.

다만 그 회차의 결과가 왜 못 쓰는 값인지도 같이 드러났다 — 서로 다른 선수인
`12172` 와 `87297` 의 기록이 **완전히 똑같았다**(둘 다 Fulham · 5경기 · 1골).
core eventlog 경로로 받은 값은 각각 4경기/5경기로 갈린다. 교체 판단은 그대로
유효하다.


### 동명이인 — 소속팀만으로는 못 가른다 (2026-09-23)

리스 제임스 사진이 규칙을 고친 뒤에도 그대로 남의 얼굴이었다. 두 가지가
겹쳐 있었다.

#### ① 틀린 사진이 영원히 남는 구조

이어받기(`betterPhoto`)는 **출처 등급만** 본다. 예전 느슨한 규칙이 박아 둔
사진도 `kind: 'cutout'`(최고 등급)이라, 규칙을 고쳐 새로 못 찾게 되어도
이어받기가 그 사진을 계속 이긴다. 위키 사진이 눌러앉던 문제를 등급으로
고쳤더니 이번엔 **틀린 컷아웃이 눌러앉았다.**

`sportsdbPhoto` 를 세 가지로 답하게 바꿨다.

| 값 | 뜻 |
|---|---|
| `{url, kind}` | 찾았다 |
| `null` | 확인했고, 지금 규칙으로는 쓸 만한 후보가 없다 |
| `undefined` | 확인하지 못했다 (한도·네트워크) |

`null` 일 때만 이어받은 TheSportsDB 사진을 의심해 버린다. 한도에 걸려
확인조차 못 한 회차(`undefined`)에 멀쩡한 사진을 날리면 안 된다.

#### ② 위키백과에도 같은 함정이 있었다

TheSportsDB 만 고치면 끝이 아니었다. `Reece James footballer` 로 검색하면
`Reece James (footballer, born 1993)`(셰필드 웬즈데이)와 `Reece James`(첼시,
1999년생)가 **둘 다** 나온다. 예전 코드는 "축구 선수이고 이름이 맞으면 첫
번째" 라서 검색 순위가 바뀌는 대로 1993년생을 집을 수 있었다 — 같은 얼굴이
위키 경로로 다시 들어온다.

**가를 수 있는 건 나이뿐이다.** 이름·국적·포지션이 전부 같다. ESPN 팀
로스터가 `age` 를 준다(첼시 28명 중 26명, 코리안리거 21/21). 후보의 생년과
대조한다 — TheSportsDB 는 `dateBorn`, 위키백과는 설명의 `(born 1999)`.
생일이 지났는지 모르므로 두 해를 허용하고, 근거가 없으면(나이나 생년 중
하나가 없으면) 막지 않는다 — **확인 못 한 것과 틀린 것은 다르다.**

나이를 아는데 맞는 후보가 하나도 없으면 사진을 포기한다.

#### 확인한 세 명 (2026-09-23 실측)

| 선수 | 나이 | TheSportsDB | 위키백과 | 결과 |
|---|---|---|---|---|
| 리스 제임스 | 26 | Sheffield Wednesday **1993년생**뿐 → 거부 | `[1999]` 선택 (`[1993]` 거부) | 위키 · 올바른 인물 |
| 웨슬리 포파나 | 25 | **등록 없음** (`Fofana` 는 포르투의 Seko Fofana 만 → 거부) | `[2000]` | 위키 · 올바른 인물 |
| 조렐 하토 | 20 | Chelsea `2006-03-07` 컷아웃 ✓ | `[2006]` | TheSportsDB 컷아웃 |

주앙 페드루는 팀 로스터 경로로 잡힌다(이름 검색은 포르투갈 3부의 다른
Joao Pedro 만 준다).

#### 알아 둘 한계

- 무료 키의 `lookup_all_players` 는 **10명까지**만 준다(이름 알파벳 순).
  첼시는 Aarón Anselmino ~ Jordan Henderson 까지다. 나머지는 이름 검색에

- `searchplayers.php?t=<팀>` 은 무료 키에서 0건을 돌려준다 — 팀 단위로 더
  많이 받을 방법이 없다.


### Summary 탭 — 한 화면 랜딩 (2026-09-23)

앱에 들어오면 처음 보이는 화면. 팀 탭을 하나씩 들어가지 않아도 "지금 무슨
일이 있나" 가 한 화면에 들어온다.

**구조는 팀에 속하지 않는다.** Summary 는 일곱 팀을 가로지르므로 팀별 탭
목록에 넣을 수 없다. `App` 에 `view: 'summary' | 'team'` 을 두고, 팀 스위처

| 섹션 | 하는 일 |
|---|---|
| 매치데이 히어로 | 일곱 팀의 다음 경기를 비교해 가장 가까운 팀을 큰 카드로. 작은 카드를 누르면 히어로가 바뀌고 캘린더도 그 주로 이동한다. 카운트다운은 히어로에만 |
| 주간 캘린더 | 월~일 7열. 이동 범위 제한 없음. 경기 줄은 **팀 컬러** 왼쪽 띠 |

| 이달의 경기 결과 | 이번 달 종료 경기를 시간 역순. 누르면 득점자가 펼쳐진다 |

#### 대한민국

일정 세 곳(히어로·캘린더·이달의 결과)에 모두 나오고 득점자도 펼쳐진다.
다만 **대회 순위와 선수 순위에는 넣지 않는다** — 국가대표는 리그가 없고
클럽 대회 순위표에 섞을 자리가 없다.

#### ⚠️ brand 가 아니라 accent 다

처음에 팀 강조색으로 `theme.brand` 를 썼더니 뉴캐슬(#241F20, 거의 검정)과
토트넘(#132257, 짙은 남색) 행의 순위 숫자와 승점이 어두운 표 위에서 그대로
묻혔다. `targets.ts` 가 이미 적어 둔 대로 **accent 가 "어두운 배경 위
텍스트·보더용으로 밝기를 올린 변형"** 이다. 순위표·선수순위·캘린더 띠·
카드 테두리 전부 accent 를 쓴다.

#### ⚠️ 경량 순위 파일에 골·선수기록을 다시 넣었다

`table-{lg}.json` 은 일정 탭이 3.2MB 리그 파일을 받지 않게 만든 경량본이라
`__goals` / `__stats` 를 빼 두었다. 그런데 Summary 의 **선수 순위가 바로 그
두 값으로 만들어진다**(`deriveLeaders`) — 빼면 순위가 통째로 빈다.
실측으로 확인하고 다시 넣었다.

| 리그 | 원본 | 경량(골·스탯 제외) | 경량(포함) |
|---|---|---|---|
| eng.1 | 3,264KB | 236KB (gz 9KB) | **267KB (gz 14KB)** |
| esp.1 | 3,389KB | 233KB (gz 9KB) | **277KB (gz 16KB)** |
| uefa.champions | 1,428KB | 204KB (gz 10KB) | **219KB (gz 13KB)** |

30KB(gzip 5KB) 더 받고 원본의 1/12 을 유지한다.

#### 같은 경기가 두 번 세어지던 자리

첼시 vs 맨유처럼 **우리 팀끼리 맞붙으면 두 팀의 일정 파일에 같은 경기가
들어 있다.** 그대로 두면 캘린더 한 칸에 같은 경기가 두 줄, 이달의 결과에도
두 번 나온다. `matchesByDay` / `monthResults` 가 경기 id 로 한 번만 남긴다
(테스트로 고정).

#### 화면 검증

컨테이너에서 실제로 빌드해 Playwright 로 렌더하고 구조를 셌다 —
히어로 1 + 카드 5, 순위 20행 중 우리 팀 5행 강조, 선수순위 24행 중 우리 팀
10행 강조, 이달의 결과 22경기, 가로 스크롤 없음. 뉴캐슬·토트넘이 안 보이던
것도 이 과정에서 잡았다.


### Summary 탭 2차 — 가시성 손보기 (2026-09-23)

랜딩 화면을 실제로 놓고 보니, 쓸 수 없는 정도는 아니어도 "읽히지 않는"
자리가 여럿 있었다. 하나씩.

**어두운 엠블럼.** 토트넘과 리버풀은 어두운 배경 위에서 형체가 사라진다.
짐작이 아니라 실제 ESPN 로고를 캔버스로 읽어 확인했다 — 평균 밝기
토트넘 35 / 리버풀 53, **어두운 픽셀 비율은 둘 다 100%** (뉴캐슬 113·37%,
첼시 147·44%, 레알 161·0%). 즉 밝기 보정으로는 못 살린다. 사각 테두리를
두르면 엠블럼이 아니라 상자가 보이므로, 알파 채널을 따라가는
`drop-shadow` 를 **1px 네 겹 + 4px 부드러운 후광**으로 쌓아 실루엣만
흰 선으로 그렸다. 후보를 넷 그려 놓고 실제 렌더를 비교해 골랐다 —
한 겹·두 겹은 22px 크기에서 사라지고, `brightness()` 를 섞으면 레알처럼
밝은 엠블럼이 하얗게 날아간다. 밝은 엠블럼에 거의 영향이 없는 것이
이 방식을 고른 이유다.

**이달의 경기 결과.** 우리 일곱 팀을 항상 왼쪽에 두고 상대를 오른쪽에
두었는데, 1440px 에서 대진 블록이 왼쪽 292px 만 쓰고 나머지 850px 이
빈 채로 남아 한 줄의 왼쪽 끝과 오른쪽 끝이 눈으로 이어지지 않았다.
블록을 820px 로 잡아 가운데로 모으고, 양쪽 `1fr` + 가운데 고정폭으로
바꿔 **스코어와 엠블럼이 모든 줄에서 같은 세로선**에 서게 했다. 약어
대신 팀 이름을 쓰고 H/A 배지를 HOME/AWAY 로 늘렸다.

좁은 화면에서는 이 결정이 그대로 역효과였다. 390px 에서 폭이 없으니
말줄임이 걸려 `M..` `R..` 만 남았다. CSS 로는 글자를 줄일 수 없으므로
풀네임과 약어, HOME/AWAY 와 H/A 를 **둘 다 마크업에 넣고** 760px 에서
갈아 끼운다. DOM 이 조금 늘어나는 대신 어느 폭에서도 읽을 수 있다.

**나머지.** 히어로 카드는 팀 탭과 같은 언어로 다시 그렸고(팀명 아래
대회 순위 · W/D/L, 경기장은 킥오프 시각과 같은 줄에 붙지 않게 한 줄을
차지한다), 나머지 카드는 3열 2행으로, 순위표 하이라이트는 `theme.brand`
대신 `theme.accent` 로 바꿨다 — 뉴캐슬(#241F20)·토트넘(#132257)은 brand
가 거의 검정이라 하이라이트가 보이지 않았다.

**프리미어리그 선수 순위가 비어 있던 것**은 디자인이 아니라 데이터였다.
슬림하게 줄인 `table-{리그}.json` 이 `__goals`/`__stats` 를 빼고 있었다.
되살리면서 용량을 쟀다 — eng.1 기준 원본 236KB→267KB, gzip 9KB→14KB.
5KB 로 리그 전체 득점·도움 순위를 사는 거래라 받아들였다.

검증은 컨테이너에서 빌드해 Playwright 로 1440×1000 과 390×844 를 각각
렌더하고 DOM 을 센 결과다 — 데스크톱 `restCols 3`, 모바일 `restCols 1`,
양쪽 다 가로 넘침 `0`. 컨테이너는 외부 이미지가 막혀 있어 **진짜 로고
확인은 배포본을 브라우저로 열어서** 따로 했다.

### 강조는 좁혀야 강조다 (2026-09-23, 3차)

엠블럼 윤곽 강조를 모든 팀에 주고 나니, 프리미어리그 순위표 스무 줄이
전부 빛났다. 그러면 그건 강조가 아니라 배경이다. 범위를 좁혔다.

- 기본값은 **우리 일곱 팀만** (`OUR_TEAM_IDS`). 상대 팀 엠블럼은 그대로다.
- 한 팀만 보는 화면에서는 그것도 넓다. 팀 탭 순위표·선수 순위에서는
  **선택된 그 팀 하나만** 빛난다 — `Crest` 에 `glow` 를 넘겨 호출부가
  기본 규칙을 덮어쓴다. Summary 처럼 우리 팀이 섞인 표는 넘기지 않아
  일곱 팀 전부가 살아 있다.

팀 탭 선수 순위에도 순위표와 같은 규칙을 넣었다. 대회 전체 득점·도움
표에서 우리 선수 줄을 팀 컬러로 세운다 — "우리 선수가 몇 위인가" 는
스무 줄을 읽어 내려가며 이름을 찾을 일이 아니다.

이달의 경기 결과는 가운데 정렬을 되돌렸다. 폭만 팀 이름이 들어갈 만큼
(196px) 넓힌 고정 3열이라, 왼쪽에서 시작하면서도 스코어와 엠블럼은
어느 줄에서나 같은 세로선에 선다.

**논-히어로 카드의 킥오프.** 여섯 장을 훑어도 날짜가 안 잡혔다 —
경기장과 같은 10.5px 회색 한 줄에 섞여 있었기 때문이다. 킥오프만
팀 컬러 스트립으로 떼어 내고 앞에 D-day 칩을 세웠다. 남은 날짜는
시간 차가 아니라 **KST 달력 날짜**로 센다 (`daysUntilKst`) — 시간으로
세면 "오늘 밤 23시" 와 "내일 새벽 1시" 가 둘 다 0일이 되어, 새벽 경기가
많은 이 화면에서는 어느 쪽이 오늘인지 알 수가 없다.

### 색이 뜻을 갖게 (2026-09-23, 4차)

**히어로 글로우.** 배경 사진을 가리지 않으려고 Summary 히어로의 글로우를
빼 두었는데, 빼고 보니 그냥 어두운 상자였다. 해법은 없애는 게 아니라

로 옅게 깔아 공이 비쳐 보이게 두고, 팀 컬러는 `box-shadow`

**주간 캘린더 펄스닷.** 월간 캘린더의 `.cal__pulse` 와 같은 ping 애니메이션을

말해 주지 못한다. 처음엔 칸 오른쪽 위에 절대 배치했다가 날짜 숫자를 덮어서,
머리줄 안에 흐름대로 넣었다.

**이달의 결과 — 정렬.** HOME/AWAY 배지와 W/D/L 칩이 줄마다 좌우로 밀려

```
우리 쪽  [배지 48] [이름 1fr 우정렬] [엠블럼 22]
상대 쪽  [엠블럼 22] [이름 1fr 좌정렬] [W/D/L 17]
```

이제 배지·엠블럼·스코어·칩이 전부 같은 세로선에 선다. 승패는 한 글자
칩으로 붙였다 — 스무 줄을 훑을 때 색만 봐도 잡힌다.

**스코어 색.** 오래 고민한 자리다. 승패색(초록·노랑·빨강)으로 칠하면 W/D/L
칩과 같은 말을 두 번 하게 되고, 한 줄에 같은 색이 두 번 나와 오히려 안
읽힌다. 팀 컬러 하나로 통일하면 어느 쪽이 우리 골인지 알 수 없다.
그래서 **"누구 골인가" 로** 칠하기로 했다 — 우리 득점은 팀 컬러, 상대
득점은 흰색. 승패는 칩이 말한다. 같은 규칙을 Summary 매치데이 카드와
팀 탭 이달의 결과에도 넣어 앱 전체가 한 가지 색 언어를 쓴다.

**득점자 펼침.** 같은 규칙의 연장이다. 우리 득점자는 팀 컬러, 상대는 흰색,
이름 앞 팀 약어도 같은 색의 칩으로 감쌌다. 팀 컬러가 흰색에 가까운
**뉴캐슬만 상대를 하늘색**(`theme.opponent` #63C9F0)으로 바꾼다 — 아니면
둘 다 흰색이 된다. Summary 에서는 `--accent`/`--opp` 를 경기 줄마다 그 팀
기준으로 갈아 끼운다. 앱 전역 값은 "지금 고른 팀" 이라 일곱 팀이 섞인
목록에서는 뜻이 없다.

### 봇이 충돌 마커를 배포했다 (2026-09-23)

새벽에 사이트의 일정·뉴스가 통째로 비었다. 방금 올린 CSS 때문인 줄 알았는데
아니었다. 배포된 `meta.json` 을 열어 보니 이렇게 들어 있었다.

```
<<<<<<< Updated upstream
{"generatedAt":"2026-09-23T01:48:08.276Z", ...}
=======
{"generatedAt":"2026-09-23T01:48:32.584Z", ...}
>>>>>>> Stashed changes
```

일정 7개, 뉴스 7개, meta 까지 **열다섯 개 JSON 에 병합 충돌 마커가 그대로**
커밋돼 있었다. `JSON.parse` 가 죽으니 로더는 조용히 `source:'none'` 으로
떨어지고, 화면은 "예정된 경기가 없습니다" 만 남는다. 파일은 200 으로
잘 내려오고 있었다 — 그래서 네트워크만 봐서는 안 보였다.

**원인.** 두 스냅샷 워크플로의 커밋 단계가 이랬다.

```
git pull --rebase --autostash
git add web/public/data
```

`snapshot`(빠름)과 `snapshot-leagues`(느림)는 concurrency 그룹이 달라서
**동시에 이 단계에 들어올 수 있다**. 한쪽이 먼저 밀어 넣은 뒤 다른 쪽이
pull 하면, autostash 가 되살아나며 같은 파일에서 충돌한다. 이때 git 은
실패로 끝내지 않고 **파일 안에 마커를 남긴 채** 작업 트리를 돌려준다.
바로 다음 줄의 `git add web/public/data` 가 그걸 그대로 담았고, 커밋됐고,
배포됐다. 마커를 넣은 커밋(`f1c5c1e`)과 그 전 회차들이 번갈아 깨졌다가
멀쩡해졌다가 한 이유도 이것이다 — 겹칠 때만 터지는 경합이다.

**고친 것.**

1. **스태시를 걷어냈다.** 스냅샷 산출물은 매 회차가 파일 전체를 새로 쓴다.
   병합할 것이 애초에 없다. 그러니 먼저 커밋하고, 푸시가 거절되면
   `git rebase -X theirs origin/main` 으로 우리 커밋을 위에 얹고 다시 민다
   (최대 3회). 데이터 충돌은 항상 지금 막 뜬 값이 옳고, 이 커밋은
   `web/public/data` 만 건드리므로 소스에는 닿지 않는다.
2. **커밋 직전 안전핀.** 스테이징된 데이터에 `^<<<<<<< ` / `^=======$` /
   `^>>>>>>> ` 가 하나라도 있으면 커밋하지 않고 잡을 실패시킨다.
3. **배포 관문.** `scripts/check-data.mjs` 가 `web/public/data` 의 모든
   JSON 을 파싱해 본다 — 마커, 빈 파일, 잘린 JSON. `deploy-pages.yml` 이
   빌드 전에 이걸 돌리므로, 원인이 무엇이든 **깨진 데이터는 배포로 넘어가지
   못한다**. 실패하면 사이트는 직전의 멀쩡한 버전을 계속 보여 준다.
   수집 직후(스냅샷 잡)와 CI 에서도 같은 검사를 돌린다.

교훈은 3번이다. 1·2번은 이번 원인을 막지만, **다음 원인은 다른 모양일 것**
이다. 관문은 원인을 몰라도 막는다.

### 역대 상대전적 — ESPN 은 알고 있었다 (2026-09-23, 6차)

대한민국 탭의 최근 5경기 카드 오른쪽이 늘 빈 상자였다. 상대전적 칸인데
경기가 0개였기 때문이다.

우리는 맞대결을 **팀 일정을 시즌 단위로 거슬러 올라가** 추려 왔다. 클럽은
3시즌, 국가대표는 13시즌. 그런데 국가대표는 한 상대를 십수 년에 한 번
만난다 — 한국-에콰도르의 마지막 맞대결은 **2010년 5월 16일**이라 13시즌을
뒤져도 안 잡혔다.

ESPN 요약(`summary`)을 열어 보니 답이 이미 들어 있었다.

```json
"seasonseries": [{
  "type": "head-to-head",
  "summary": "KOR leads series 1-0",
  "seriesScore": "1-0",
  "totalCompetitions": 1,
  "events": [{ "id": "289188", "date": "2010-05-16T10:00:00Z", ... }]
}]
```

우리가 이미 받고 있던 응답이다(`lastFiveGames` 를 여기서 꺼내 쓴다).
`scripts/lib/h2h.mjs` 를 새로 두고 `seasonseries` 의 head-to-head 항목만
`compactGame` 과 같은 모양으로 편 뒤, 일정에서 모은 것과 **경기 id 로
중복을 없애며** 합친다. 순서에 뜻이 있다 — 일정 쪽이 대회 이름을 갖고
있으므로 앞에 두고, 시리즈는 일정에 없는 옛 경기만 보태게 뒤에 둔다.
아직 안 치른 경기(=이번 맞대결 자신)가 `events` 에 섞여 오므로
`statusType.completed` 로 거른다. 테스트 8개.

라벨도 고쳤다. "역대"/"최근 세 시즌"을 팀 종류로 정하던 것을, **실제로
보여 주는 것**에서 뽑는다 — 시즌 창보다 오래된 경기가 하나라도 섞였으면
'역대' 다. 클럽이라도 옛 컵 경기가 딸려 오면 "최근 세 시즌 5경기" 는
거짓말이 된다. ESPN 이 적어 준 한 줄(`KOR leads series 1-0`)도 그대로 옮긴다.

그래도 맞대결이 정말 하나도 없는 상대는 있다. 그때는 오른쪽 268px 칸을
비워 두지 않고 **한 칸으로 접는다** — 빈 상자는 정보가 아니다.

**같이 손본 것.** 주간 캘린더에서 고른 경기 타일의 펄스를 세게 했다.
팀 캘린더의 막대는 6px 라 빛만으로 충분했지만 이 타일은 덩치가 커서 같은
세기로는 거의 안 보였다 — 퍼지는 링 + 더 센 글로우 + 3.5% 확대를 겹쳤다.
그리고 이달의 결과에서 AWAY 배지를 어둡게 둘 이유가 없어서, HOME 은 팀
컬러로 채우고 AWAY 는 **밝은 중립색**으로 또렷하게 바꿨다. 색이 다른 것
만으로 홈·원정은 충분히 갈린다.

### 지난 경기를 누르면 캘린더가 날아갔다 (2026-09-23, 7차)

주간 캘린더에서 **지난 경기**를 누르면 캘린더가 엉뚱한 주로 튀었다.

`board`(매치데이 히어로의 재료)는 팀별 **다음 경기**만 담는다. 그래서
지난 경기를 눌러 그 팀을 고르면, 히어로는 누른 그 경기가 아니라 **그 팀의
다음 경기**가 된다. 히어로가 바뀌면 그 경기가 있는 주로 캘린더를 옮기는
이펙트가 걸려 있으니, 방금 누른 자리에서 미래로 튕겨 나간다.

가드는 있었다 — `lastHero.current = list[i].match.id`. 그런데 이펙트가
비교하는 값은 **히어로 경기 id** 다. 누른 경기와 히어로 경기가 서로 다른
경우가 정확히 이 버그의 조건이라, 가드가 걸릴 리가 없었다. 실제로 히어로가
될 경기의 id(`board.find(...)`)를 미리 적어 두는 것으로 고쳤다.

**주간 캘린더 호버 미리보기.** 팀 탭 캘린더에만 있던 득점자 미리보기를
주간 캘린더 타일에도 붙였다. 카드 내용은 `MatchPopCard` 로 꺼내 두 캘린더가
같은 것을 쓴다 — 같은 모양을 두 번 적으면 한쪽만 고쳐지는 날이 온다.

위치 잡는 방식만 다르다. 월간은 `.cal` 이 `overflow: visible` 이라 날짜 칸
기준 absolute 로 띄우면 됐는데, `.wcal` 은 둥근 모서리 때문에
`overflow: hidden` 이라 그대로 하면 **잘려 나간다**. 그래서 타일의
`getBoundingClientRect()` 로 좌표를 재서 `position: fixed` + 포털로 body 에
붙인다. 위쪽에 260px 이 안 남으면 아래로 뒤집고, 좌우는 화면 안으로 클램프한다.
터치 기기에는 호버가 없으므로 (`hover: hover`) 데스크톱에서만 뜬다.

### 히어로는 "고른 경기" 여야 한다 (2026-09-23, 8차)

주간 캘린더에서 다음 경기 **이후**의 경기를 눌러도 매치데이 히어로가
그대로였다. 앞의 "지난 경기를 누르면 주가 날아간다" 와 **뿌리가 같다.**

`picked` 가 팀 id 하나였고, 히어로는 늘 `board`(팀별 *다음* 경기)에서
그 팀을 찾아 꺼냈다. 그래서 무엇을 누르든 화면에 뜨는 것은 그 팀의 다음
경기였다 — 이미 그 팀이 히어로면 아무 일도 안 일어난 것처럼 보이고,
지난 경기를 누르면 미래로 튕겨 나갔다. 증상이 둘이었을 뿐 원인은 하나다.

고른 것을 **경기 단위**로 들고 있게 바꿨다.

```ts
const [picked, setPicked] = useState<{ teamId: string; matchId: string } | null>(null);
const hero = pickedUp ?? board[0] ?? null;
```

Match 객체가 아니라 **id 로** 저장하고 매번 피드에서 다시 찾는다 —
객체를 붙들고 있으면 10분마다 데이터가 갱신될 때 옛 객체가 화면에 남는다.

이제 히어로에 **끝난 경기**가 올라올 수 있다. 카운트다운을 그대로 두면
"곧 시작" 이 뜨므로, 그 자리에 결과 한 줄(`경기 종료 2-1`)을 놓고 알람
아이콘과 펄스닷을 뺀다. 스코어 색은 나머지와 같은 규칙 — 우리 득점은 팀
컬러, 상대는 흰색.

### 헤드샷이 통째로 위키로 떨어졌다 — 충돌 마커의 뒤늦은 청구서 (2026-09-23, 9차)

"맨유·토트넘·뉴캐슬·리버풀 헤드샷이 갑자기 위키 사진으로 바뀌었다."
UI 패치 탓인 줄 알았는데 아니었다. **앞서 봇이 박아 넣은 충돌 마커의
후폭풍**이다. 커밋 기록이 정확히 말해 준다.

```
01:21  0e86dae  {"cutout":22,"espn":2,"wiki":1}   ← 멀쩡
01:23  59b47ab  parse fail                        ← 충돌 마커
01:39  ddfe872  {"wiki":21,"espn":2,"(none)":2}   ← 컷아웃 전멸
```

스냅샷은 매 회차 **지난 파일에서 사진을 이어받는다**. 그런데
`prevPhotos` 가 이랬다.

```js
try { … JSON.parse(…) } catch { /* 첫 실행 */ }
```

파일이 깨져 못 읽는 것과 "아직 파일이 없다" 를 똑같이 취급했다. 01:23 의
깨진 파일을 만난 다음 회차는 **이어받을 사진이 하나도 없다고 판단**하고
전원을 처음부터 받으려 들었다. TheSportsDB 무료 키는 한 회차에 7팀을
감당하지 못하므로 앞의 두 팀만 채우고 나머지는 전부 위키로 떨어졌다.

이걸 고치면서, 같은 증상을 두 번 만든 **진짜 원인**도 함께 고쳤다.

**1. 순서가 고정이라 뒤쪽 팀은 차례가 오지 않는다.** 이 세션 맨 처음
"레알마드리드만 헤드샷" 도 같은 뿌리였다. 그때는 회로 차단과 이어받기로
*버티게* 만들었지 *공평하게* 만들지는 못했다. 이제 지난 회차에서 아직
TheSportsDB 사진이 아닌 선수를 세어 **많이 빈 팀부터** 돈다
(`photoNeedOrder`). 지금 상태로 돌리면 리버풀(23) → 대한민국(21) →
첼시(6) → 토트넘(4) → 맨유(3) → 레알·뉴캐슬(0) 순이다.

**2. 예산을 이미 가진 사람에게 쓰고 있었다.** 이름 검색은 선수 한 명당
요청 한 번이다. 7팀 × 28명이면 190번이고, 한도는 그 훨씬 전에 걸린다.
이미 컷아웃을 들고 있는 선수에게는 쓰지 않는다. 다만 오답(리스 제임스
자리의 남의 얼굴)을 걷어낼 길은 남겨야 하므로 선수를 여섯 무리로 나눠
**회차마다 한 무리씩** 다시 확인한다(`dueForReverify`, 여섯 시간에 한 바퀴).

**3. 가장 위험한 자리를 표로 박고 테스트로 잠갔다.** 사진을 고르는 규칙은
`choosePhoto` 하나로 모았다. 핵심은 `null`(물어봤고 없다)과
`undefined`(못 물어봤다)의 구분이다 — 전자는 이어받은 컷아웃을 의심해
버리고, 후자는 **절대 건드리지 않는다**. 이 줄을 손으로 쓰다가 네 팀의
컷아웃을 한 회차에 날린 적이 있으니 이제 테스트가 지킨다.

**4. `sportsdbRoster` 도 같은 구분이 없었다.** 한도에 걸려 못 받은 것과
"팀은 찾았는데 선수가 없다" 가 둘 다 `[]` 였고, 실패까지 캐시해 그 회차
내내 같은 팀을 영영 못 받았다. `undefined` 로 갈라내고 실패는 캐시에서 뺀다.

**되살리기.** 고쳐 놔도 TheSportsDB 로 다시 채우려면 몇 시간이 걸린다.
옛 컷아웃은 git 에 그대로 남아 있으므로 `scripts/restore-photos.mjs` 로
`0e86dae` 에서 끌어왔다 — 판정은 스냅샷과 같은 `betterPhoto` 라 되살리기가
데이터를 뒤로 되돌리지 않는다. **101명**이 돌아왔다(맨유 22 · 뉴캐슬 26 ·
토트넘 22 · 대한민국 24 · 첼시 6 · 리버풀 1). 리버풀은 애초에 채워진 적이
없는 막내라 다음 회차에 1번으로 돌아간다.

### 사비올라와 전신 사진 (2026-09-23, 10차)

"첼시 포파나와 토트넘 사비가 전혀 다른 사람 같다." 둘을 확인해 보니 **원인이
서로 달랐다.** 하나는 진짜 남의 얼굴이고, 하나는 본인인데 못 알아볼 사진이다.

**사비 — 진짜 남의 얼굴.** 박혀 있던 컷아웃 파일 `3100367.png` 의 주인을
TheSportsDB 에 물었더니 **하비에르 사비올라(1981년생, 은퇴)** 였다. 화면에
띄워 보니 마흔 줄 남자 얼굴이 맞았다. 이름 검색이 "Savio" 로 사비올라를
물어 온 것이다 — 2003년생 브라질 윙어 자리에.

규칙은 이미 이걸 걸러낸다(소속팀 일치 + 생년 타당성). 그런데도 다시
들어온 경로가 **내가 바로 앞 커밋에서 돌린 복구 스크립트**였다.
`restore-photos.mjs` 가 옛 커밋에서 좋은 사진을 끌어오면서 이 오답도 같이
끌어왔다. 규칙을 조이는 것만으로는 부족하다 — 이어받기는 등급만 보고
도로 물어 오고, 복구는 옛 커밋에서 도로 끌어온다.

그래서 **확인된 오답 목록**(`BAD_PHOTO_FILES`)을 두고 `betterPhoto` 에서
막는다. 사진이 바뀌는 길은 전부 그 함수를 지나므로 한 곳이면 된다.
키는 파일 이름이다 — 호스트가 바뀌어도(thesportsdb.com → r2.thesportsdb.com)
파일 이름은 그대로였다. 테스트 5개로 잠갔다.

**포파나 — 본인인데 못 알아볼 사진.** 위키 문서를 확인하니
"Wesley Fofana (footballer) · French footballer (born 2000)" — 첼시 수비수
본인이 맞다. 문제는 그 사진이 **542×1164(2.15:1) 짜리 2022년 레스터 경기
전신 사진**이라는 것이다. 원형 아바타로 잘라 놓으면 얼굴이 거의 남지 않는다.
사람이 아니라 사진이 문제였다.

위키 대표 이미지는 얼굴 사진이 아닐 때가 많다. 이제 원본 세로/가로 비율이
**1.8을 넘으면 후보에서 뺀다** — 알아볼 수 없는 사진을 박느니 이름 배지로
두는 편이 낫다. (TheSportsDB 는 축구 선수 Fofana 를 아예 모르고 — 같은 이름의
럭비 선수만 있다 — ESPN 헤드샷도 404 라, 지금으로선 배지가 정답이다.)

**덧붙여 배운 것.** 140명을 한꺼번에 API 로 검증하려다 실패했다. 무료 키가
중간부터 빈 응답을 주기 시작해서 "확인 못 함" 과 "오답" 이 구분되지 않았다 —
브루노 페르난데스까지 수상해 보였다. 예산 한계는 데이터를 고칠 때도 똑같이
걸린다는 걸 잊고 있었다. 파일 이름 형식(`<6자><10자리 epoch>.png`)으로 먼저
걸러 이상한 한 건만 정밀 확인하는 편이 빠르고 정확했다.

### 좁은 화면의 선수 순위 — 서브탭 (2026-09-23)

득점·도움·공격 포인트 세 표는 900px 아래에서 세로로 쌓였다. 여덟 줄짜리
표 세 개가 이어 붙으니 "득점 1위" 를 보려고 두 표를 지나쳐야 했다.
서브탭으로 바꿔 한 번에 하나만 보인다.

고르는 상태는 리액트가 들고 `data-active` 로 내려 주지만 **감추는 일은 CSS**
가 한다. 뷰포트를 자바스크립트로 재면 넓은 화면에서도 쓸데없이 다시
그리고, 창 크기를 바꿀 때 한 박자 늦게 따라온다. 미디어 쿼리 안에서만
`data-active` 를 보게 해 두면 넓은 화면은 손도 대지 않은 채 셋 다 나온다.
`LeaderBoard` 한 곳을 고쳐 Summary·팀 순위·선수 스탯 세 자리가 함께 바뀐다.

### 포털은 테마를 물려받지 않는다 · 뉴캐슬의 흰색 (2026-09-23, 11차)

**호버 득점자가 전부 레알 색이었다.** 주간 캘린더 미리보기는 `.wcal` 의
`overflow: hidden` 을 피하려고 **포털로 `document.body` 에 붙인다**. 그런데
앱은 테마 변수(`--accent`·`--opp`)를 컴포넌트 트리 안쪽 div 에 심는다.
포털은 그 바깥이므로 변수를 못 받고 `:root` 기본값 — 첫 팀인 레알의 노랑 —
으로 떨어졌다. 리버풀 경기를 봐도 득점자 약어가 노랬던 이유다.
카드를 띄울 때 그 경기의 팀 색을 style 로 직접 얹어 해결했다.
포털을 쓸 때마다 다시 만날 함정이라 주석으로 박아 뒀다.

**스코어·킥오프가 안 보였다.** 칸에서 제일 먼저 찾는 값인데 11px 회색
(`--text-lo`)이었다. 종료 스코어는 13.5px 흰색으로, 예정 킥오프는 12px
**팀 컬러를 섞은 밝은 색**으로 갈랐다 — 크기만 키우면 둘이 같아 보이므로
"끝난 경기" 와 "앞으로 할 경기" 가 색으로도 구분되게 했다.

**뉴캐슬은 흰색이라 강조가 안 된다.** 흑백 줄무늬 팀이라 어두운 배경에서
쓸 수 있는 쪽이 흰색(#E6EAF2)뿐인데, 그건 본문 글씨 색과 사실상 같다.
스무 줄짜리 순위표에서 우리 줄만 흰 글씨로 칠해 봐야 나머지 열아홉 줄과
구분되지 않는다.

팀 이름을 코드에 박는 대신 **색을 보고 판단한다**(`lib/mark.ts`). 밝기가
0.8 이상이면서 동시에 색기(chroma)가 0.15 미만일 때 — 즉 희거나 회색일 때만
— 그 팀의 보조색으로 물러난다. 뉴캐슬의 보조색은 엠블럼의 하늘색(#41B6E6)
이라 팀 정체성도 지킨다. 두 조건을 **모두** 보는 것이 요점이다: 레알의
노랑(#FFCF3D)은 밝기가 0.8을 넘지만 색이 뚜렷해서 아무 문제가 없다.
나중에 흰색 계열 팀이 늘어도 그대로 동작한다. 테스트 9개.

한 팀만 보는 팀 탭 순위표에는 `focusColor` 를 새로 받는다 — 기존 `focusTeams`
를 재활용하면 "여러 팀이 섞인 표" 로 인식돼 엠블럼 강조가 일곱 팀 전부로
번진다(앞서 좁혀 놓은 것이 도로 풀린다).

### autopush.bat — 커밋은 되는데 푸시가 안 되는 문제 (2026-09-23)

Claude 는 격리된 리눅스 VM 안에서 이 폴더를 마운트해 쓴다. 그 VM 에서
확인한 상태는 이렇다.

| | |
|---|---|
| `git commit` | **된다** — 지금까지의 커밋은 전부 거기서 만들어졌다 |
| github.com 도달 | 된다 (`http 200`, 익명 `fetch`·`pull` 정상) |
| `git push` | **안 된다** — 자격증명이 없다 |

`credential.helper`·`~/.git-credentials`·`~/.netrc`·`~/.ssh`·`gh` 가 전부
없고, 여러분의 자격증명이 있는 **Windows 자격증명 관리자**는 그 VM 에서
보이지 않는다(`/mnt` 에는 연결 폴더 하나뿐이고 `cmd.exe` 도 없어 `.bat` 을
실행할 수도 없다). 클라우드 컨테이너 쪽 토큰은 git 프록시가 막는다 —
`repository is not in this session's authorized set`.

즉 **네트워크가 아니라 인증 한 칸**이 빈다. 그리고 토큰은 Claude 가 다루지
않는 편이 안전하다.

그래서 반대 방향으로 막는다. 자격증명이 이미 있는 **Windows 쪽에 감시자**를
두면, Claude 가 커밋하는 순간 그쪽이 밀어 올린다.

```
autopush.bat              60초마다 확인 (창을 닫으면 멈춘다)
autopush.bat once         한 번만 확인하고 종료 (작업 스케줄러용)
autopush.bat install      5분마다 도는 작업 스케줄러 등록
autopush.bat uninstall    그 작업 제거
```

설계에서 지킨 것:

- **커밋은 절대 만들지 않는다.** 이미 만들어진 커밋만 보낸다 — 커밋되지
  않은 것이 GitHub 에 올라갈 길이 없다.
- 작업 트리가 지저분하면 건너뛴다. 리베이스가 여러분의 미커밋 변경을
  휩쓸어 가지 않게.
- 리베이스가 중간에 멈춰 있으면(`.git/rebase-merge`) 손대지 않고 멈춘다 —
  자동화가 충돌을 헤집는 것이 가장 나쁘다.
- `GIT_TERMINAL_PROMPT=0` — 작업 스케줄러 안에는 입력할 콘솔이 없어서,
  자격증명을 물으면 작업이 영원히 멈춘다. 빨리 실패하게 둔다.

⚠️ **main 은 공개 저장소이고 푸시가 곧 배포다.** 이 감시자를 켜 두면
Claude 가 커밋한 것이 검토 없이 그대로 배포된다. 한 번 보고 올리고 싶으면
켜지 말고 `push.bat` 을 쓰면 된다.


### 윈도우에서 올리기 — push.bat / apply-update.bat (2026-09-16)

PC 작업으로 넘어오면서 커밋·푸시를 더블클릭으로 끝낼 수 있게 배치 파일
두 개를 저장소에 넣었다.

- **`push.bat`** — 바뀐 파일을 보여 주고, 커밋 메시지를 물어본 뒤(그냥 Enter
  치면 날짜) 커밋·푸시한다. 이 저장소는 봇이 10분마다 데이터를 커밋하므로
  push 가 자주 밀리는데, 그때마다 `git pull --rebase` 후 **최대 3번까지 자동
  재시도**한다. 처음 실행하면 커밋에 쓸 이름·이메일을 한 번 물어보고,
  `pull.rebase=true` 를 저장소에 박아 둬서 예전에 겪던 "divergent branches"
  오류가 다시 나지 않게 한다.
- **`apply-update.bat`** — 다운로드 폴더에서 가장 최근 `k-stats-hub*.tar.gz`
  를 찾아 현재 폴더에 풀고(최상위 `ksh/` 는 벗겨 낸다), 이어서 push.bat 을
  부를지 물어본다. 실행 중 자기 자신이 덮어써지면 cmd 가 오작동하므로
  압축 해제에서 자신만 제외한다.

두 파일 모두 BOM 없는 UTF-8 + CRLF 로 저장했고, `.gitattributes` 에
`*.bat text eol=crlf` 를 넣어 clone 할 때도 CRLF 로 내려가게 했다
(LF 로 내려가면 cmd 가 `goto`/라벨을 제대로 못 읽는다).
